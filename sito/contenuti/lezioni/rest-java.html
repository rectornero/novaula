Un web service
RESTful in Java

BiblioAPI prende vita: un server REST con le operazioni CRUD, scritto con il solo JDK, senza framework. Ogni byte che parte lo decidi tu.

5G TPSIHttpServer, HttpExchange, JSON, codici di stato, concorrenza

Obiettivi: realizzare con com.sun.net.httpserver un servizio REST con GET, POST, PUT e DELETE sulle risorse /api/libri e /api/libri/{id}; produrre e leggere JSON semplice; scegliere i codici di stato giusti; capire perché servono strutture dati thread-safe. Durata indicativa: 4 ore di laboratorio. Ambiente: JDK 21 con IntelliJ IDEA Community o VS Code; nessuna libreria esterna. Con JDK 11 o successivo un singolo file si esegue con java BiblioServer.java senza compilare. Si parte dal file biblioapi-design.md della lezione 8. Porta scelta: 8000, per non scontrarsi con Tomcat (8080) nella lezione 10.

Per cominciare

Se domani dovessi scrivere un'API in Java per un'azienda, con che cosa la scriveresti?

  1. Spring Boot
  2. Jakarta EE, con Jakarta REST
  3. Solo il JDK, come oggi
  4. Me la farei scrivere da un'AI
  5. Non saprei da dove iniziare
Sondaggio senza risposta giusta. In azienda la risposta più frequente è Spring Boot; Jakarta REST (ex JAX-RS) è lo standard di Jakarta EE e si usa anche con Quarkus. Oggi però usiamo il solo JDK per vedere tutto quello che i framework nascondono: il routing, i codici, gli header, la serializzazione. Chi ha scelto D: alla fine della lezione rivediamo che cosa bisogna controllare in un server scritto da un'AI.

Lo stesso endpoint, tre modi

I framework fanno con un'annotazione ciò che oggi scriviamo a mano

Spring Boot

@GetMapping("/libri/{id}")
Libro uno(@PathVariable
          int id) {…}

Il framework più usato nelle aziende Java.

Jakarta REST

@GET @Path("/libri/{id}")
Libro uno(@PathParam("id")
          int id) {…}

Lo standard di Jakarta EE, ex JAX-RS.

Solo JDK

server.createContext(
  "/api/libri", ex -> {
  // tutto a mano });

Niente magia: routing, JSON e codici sono codice nostro.

Con i framework la conversione da oggetto Java a JSON la fa una libreria (Jackson in Spring Boot, JSON-B in Jakarta EE) e i codici di stato si scelgono con ResponseEntity o Response. Il package com.sun.net.httpserver esiste dal JDK 6 ed è un modulo supportato (jdk.httpserver): non è pensato per la produzione ad alto carico, ma è perfetto per prototipi, test e didattica. Dal JDK 18 c'è anche il comando jwebserver, un server di file statici basato sulla stessa API.

Come è fatto il server

Dal socket al tuo metodo

HttpServer

Ascolta sulla porta 8000 e legge le richieste HTTP.

Contesto

Sceglie l'handler in base al prefisso del percorso: /api/libri.

Handler

Il tuo codice: guarda metodo e percorso e decide.

HttpExchange

Richiesta e risposta: header, corpo, codice.

Un Executor decide quale thread esegue l'handler. Due client possono chiamare l'API nello stesso istante: il codice deve reggere richieste concorrenti.
Senza setExecutor il server usa un solo thread di default: le richieste vengono servite una per volta. Con un pool di thread (o i thread virtuali di Java 21) le richieste sono servite in parallelo, e allora le strutture dati condivise diventano un problema: lo vediamo più avanti con il quiz sulla HashMap. Collegamento con la lezione 1 dell'unità: anche un piccolo server REST è un pezzo di sistema distribuito, con concorrenza e guasti parziali.

Il primo endpoint

Quindici righe per un web service

import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class BiblioServer {
  public static void main(String[] args) throws Exception {
    HttpServer server = HttpServer.create(new InetSocketAddress(8000), 0);
    server.createContext("/api/ping", ex -> {
      byte[] dati = "{\"stato\":\"ok\"}".getBytes(StandardCharsets.UTF_8);
      ex.getResponseHeaders().set("Content-Type", "application/json");
      ex.sendResponseHeaders(200, dati.length);   // prima gli header…
      try (var os = ex.getResponseBody()) { os.write(dati); }  // …poi il corpo
    });
    server.start();
  }
}
Punti da sottolineare. 1) L'ordine è obbligato: header e codice si impostano prima di sendResponseHeaders; dopo, si scrive solo il corpo. Impostare un header dopo non ha effetto. 2) La lunghezza va in byte, non in caratteri: "è" in UTF-8 occupa 2 byte, per questo si converte prima in byte[]. 3) Il try-with-resources chiude lo stream e completa lo scambio; se non si chiude, il client resta in attesa. 4) Il secondo argomento di create (0) è il backlog delle connessioni in coda: 0 significa valore di sistema.

Controllo: il browser mostra {"stato":"ok"}. curl mostra HTTP/1.1 200 OK, Content-type: application/json e Content-length: 14. Per /api/pong: 404, perché nessun contesto corrisponde.
Se la porta 8000 è occupata compare java.net.BindException: Address already in use; cambiare porta o chiudere l'altro server (spesso è una seconda copia dello stesso programma ancora aperta). Quiz per chi legge la documentazione

DELETE riuscita: 204 No Content. Che cosa passi come lunghezza?

  1. ex.sendResponseHeaders(204, 0)
  2. ex.sendResponseHeaders(204, null)
  3. ex.sendResponseHeaders(204, -1)
  4. Nessuna: con 204 non si chiama

Per HttpServer la lunghezza -1 significa "nessun corpo". Lo 0, che sembra naturale, significa "corpo di lunghezza sconosciuta", inviato a pezzi (chunked): con 204 il JDK corregge da solo e stampa un WARNING.

È scritto nella documentazione di HttpExchange.sendResponseHeaders: "If the response length parameter is greater than zero, this specifies an exact number of bytes to send... If the response length parameter is zero, then chunked transfer encoding is used... If the response length parameter has the value -1 then no response body is being sent." La A è il tranello: quasi tutti la scelgono. Provato con JDK 21: con 204 e lunghezza 0 la risposta parte comunque corretta, ma nella console del server compare "WARNING: sendResponseHeaders: rCode = 204: forcing contentLen = -1"; con 200 e lunghezza 0, invece, la risposta usa davvero Transfer-encoding: chunked. Meglio scrivere -1 e non affidarsi alla correzione. La B non compila (il parametro è un long primitivo). La D è sbagliata: senza sendResponseHeaders non parte nemmeno la riga di stato. Dopo un 204 bisogna comunque chiudere lo scambio con ex.close().

Il modello e le risposte

Un record, una mappa, un metodo che risponde

record Libro(int id, String titolo, String autore, int anno) {
  String toJson() {
    return "{\"id\":%d,\"titolo\":\"%s\",\"autore\":\"%s\",\"anno\":%d}"
        .formatted(id, esc(titolo), esc(autore), anno);
  }
}
static final Map<Integer, Libro> libri = new ConcurrentHashMap<>();
static final AtomicInteger prossimoId = new AtomicInteger(1);

static void rispondi(HttpExchange ex, int codice, String json) throws IOException {
  byte[] dati = json.getBytes(StandardCharsets.UTF_8);
  ex.getResponseHeaders().set("Content-Type", "application/json; charset=utf-8");
  ex.sendResponseHeaders(codice, dati.length);
  try (OutputStream os = ex.getResponseBody()) { os.write(dati); }
}
Il JSON è costruito a mano per vedere com'è fatto; esc(s) raddoppia le barre rovesciate e mette la barra davanti alle virgolette: s.replace("\\", "\\\\").replace("\"", "\\\""). Senza escape, un titolo con le virgolette romperebbe il JSON: è la stessa famiglia di problemi delle injection dell'Unità 1. In un progetto vero si usa una libreria: Jackson (com.fasterxml.jackson.core:jackson-databind) o Gson, via Maven o Gradle; con Jackson basta new ObjectMapper().writeValueAsString(libro). Il record (Java 16+) genera costruttore, getter id(), titolo()…, equals e toString. All'avvio inserire 3 libri: I promessi sposi (Manzoni, 1840), Il barone rampante (Calvino, 1957), Se questo è un uomo (Levi, 1947).

Il routing

Metodo + percorso = che cosa fare

static void gestisci(HttpExchange ex) throws IOException {
  String metodo = ex.getRequestMethod();
  String[] parti = ex.getRequestURI().getPath().split("/");  // ["", "api", "libri", "3"]
  try {
    if (parti.length == 3) {                                  // /api/libri
      switch (metodo) {
        case "GET"  -> rispondi(ex, 200, elenco());
        case "POST" -> crea(ex);
        default     -> rispondi(ex, 405, errore("metodo non consentito"));
      }
    } else if (parti.length == 4) {                           // /api/libri/{id}
      Libro l = libri.get(Integer.parseInt(parti[3]));
      if (l == null) { rispondi(ex, 404, errore("libro non trovato")); return; }
      // switch su GET, PUT, DELETE…
    } else rispondi(ex, 404, errore("risorsa non trovata"));
  } catch (NumberFormatException e) { rispondi(ex, 400, errore("id non valido")); }
}
Si registra con server.createContext("/api/libri", BiblioServer::gestisci). Il contesto fa corrispondere il prefisso del percorso, quindi anche /api/libri/3 arriva qui. Il ramo mancante: switch (metodo) { case "GET" -> rispondi(ex, 200, l.toJson()); case "PUT" -> aggiorna(ex, l.id()); case "DELETE" -> { libri.remove(l.id()); ex.sendResponseHeaders(204, -1); ex.close(); } default -> rispondi(ex, 405, ...); }. elenco() unisce i JSON dei libri ordinati per id: StringJoiner sj = new StringJoiner(",", "[", "]"); libri.values().stream().sorted(Comparator.comparingInt(Libro::id)).forEach(l -> sj.add(l.toJson())); return sj.toString(). errore(msg) restituisce {"errore":"msg"}. Miglioria per i più veloci: con il 405 aggiungere l'header Allow: GET, POST.

Per i più veloci: GET /api/libri?autore=Calvino con getQuery() e un filtro sullo stream.

Creare una risorsa

POST: leggi, valida, salva, rispondi 201

static void crea(HttpExchange ex) throws IOException {
  String corpo = new String(ex.getRequestBody().readAllBytes(), StandardCharsets.UTF_8);
  String titolo = campo(corpo, "titolo"), autore = campo(corpo, "autore");
  Integer anno = numero(corpo, "anno");
  if (titolo == null || autore == null || anno == null) {
    rispondi(ex, 400, errore("servono titolo, autore e anno")); return;
  }
  int id = prossimoId.getAndIncrement();
  Libro l = new Libro(id, titolo, autore, anno);
  libri.put(id, l);
  ex.getResponseHeaders().set("Location", "/api/libri/" + id);
  rispondi(ex, 201, l.toJson());
}
campo e numero estraggono un valore con un'espressione regolare: Pattern.compile("\"" + nome + "\"\\s*:\\s*\"([^\"]*)\"") per le stringhe e Pattern.compile("\"" + nome + "\"\\s*:\\s*(\\d+)") per i numeri; restituiscono null se il campo manca. È una semplificazione didattica: non gestisce virgolette dentro i valori, oggetti annidati o campi ripetuti. Dirlo chiaramente e mostrare che con Jackson basterebbe new ObjectMapper().readValue(corpo, Libro.class). Il PUT è quasi identico: stesso parsing, ma l'id viene dall'URI, si sostituisce il libro esistente e si risponde 200 con il JSON. Domanda: perché il server sceglie l'id e non il client? (Evita collisioni tra client diversi; se fosse il client a scegliere l'URI, il metodo giusto sarebbe PUT /api/libri/{id}.)

Puzzle

Una richiesta POST arriva al server: metti in ordine

  1. Il contesto /api/libri passa lo scambio all'handler
  2. L'handler legge metodo e percorso e sceglie crea
  3. Legge il corpo e ne estrae titolo, autore e anno
  4. Se manca un campo risponde 400 e si ferma
  5. Prende un nuovo id e salva il libro nella mappa
  6. Imposta gli header Location e Content-Type
  7. Invia il codice 201, scrive il JSON e chiude lo stream
Ordine corretto come scritto. Errori da discutere: impostare gli header dopo sendResponseHeaders (non hanno effetto), salvare prima di validare (resterebbero libri incompleti), prendere l'id prima della validazione (non è un errore grave, ma lascia "buchi" nella numerazione: va bene, gli id non devono essere consecutivi).

Quiz sulla concorrenza

Con una HashMap e un int contatore, due POST arrivano nello stesso istante. Che cosa può succedere?

  1. Due libri diversi possono ricevere lo stesso id
  2. Niente: HttpServer serve sempre una richiesta per volta
  3. Il secondo client riceve 409 Conflict
  4. La JVM se ne accorge e lancia un'eccezione

id++ non è atomico: leggi, somma, scrivi. Due thread possono leggere lo stesso valore e un libro sovrascrive l'altro. Con AtomicInteger e ConcurrentHashMap le operazioni sono sicure tra thread.

La B è vera solo senza setExecutor (un solo thread): appena si usa un pool, come facciamo con server.setExecutor(Executors.newVirtualThreadPerTaskExecutor()), le richieste sono parallele. La D è il tranello: la JVM non rileva le race condition; una HashMap modificata in concorrenza può perdere dati o corrompersi senza alcun errore. La C confonde un codice HTTP (deciso da noi) con un problema interno. Per provarlo: un ciclo di 1000 POST in parallelo da un client con sendAsync (lezione 10) e contare i libri.

Menti che ci hanno preceduto

Prima il codice, poi le discussioni

Oggi

Java 21 ha introdotto i thread virtuali: con Executors.newVirtualThreadPerTaskExecutor() ogni richiesta ha il suo thread leggerissimo, gestito dalla JVM. Un server ne regge migliaia senza cambiare stile di programmazione.

Originale: "Talk is cheap. Show me the code.", scritto da Torvalds sulla linux-kernel mailing list in una discussione tecnica il 25 agosto 2000; traduzione nostra. Lo spirito è quello del laboratorio: un'API si discute meglio quando c'è un prototipo che risponde. I thread virtuali sono stati definitivi con la JEP 444 in Java 21 (2023, progetto Loom). Un thread di piattaforma corrisponde a un thread del sistema operativo e occupa memoria per lo stack; i thread virtuali vengono montati su pochi thread di piattaforma solo quando lavorano, e si "smontano" quando aspettano I/O.

Il server scritto da un'AI

Che cosa controllare prima di fidarsi

  • I codici: 201 e Location, 204, 400, 404, 405.
  • La validazione dell'input, prima di salvare.
  • L'escape del JSON e dei caratteri speciali.
  • Le strutture dati condivise tra thread.
  • Nessun segreto o password scritti nel codice.

Oggi

Un agente di programmazione come quelli visti nella lezione su Claude Code scrive un server come questo in pochi secondi. Ma il codice va letto e provato: chi firma il progetto sei tu. Chiedi all'agente anche i test con curl e controlla che passino davvero.

Collegamento al deck claude-code già visto in 5G. Esperimento possibile: far generare all'agente lo stesso server e confrontarlo con quello scritto in classe usando la lista a sinistra come griglia. Errori che i modelli fanno spesso in questo contesto: 200 invece di 201, lunghezza 0 per il 204, HashMap non sincronizzata, JSON costruito senza escape. Non è una regola fissa: dipende dal modello e dalla richiesta, ed è per questo che si verifica.
