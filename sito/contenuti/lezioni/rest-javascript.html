Per cominciare

Un po' di storia

Dalle pagine che si ricaricano alle pagine che chiedono dati

1999 · XMLHttpRequest

Microsoft lo crea per la webmail di Outlook in Internet Explorer 5. Poi lo copiano tutti i browser.

2005 · "Ajax"

Jesse James Garrett dà un nome alla tecnica che fa funzionare Gmail e Google Maps.

2015 · fetch

Un'interfaccia moderna, basata sulle Promise, arriva nei browser principali.

Crockford intendeva che la sintassi degli oggetti letterali di JavaScript esisteva già: lui la riconobbe come formato di scambio, le diede un nome e un sito (json.org, 2002 circa); poi divenne la RFC 4627 nel 2006 e lo standard ECMA-404. La frase viene dal talk "The JSON Saga" tenuto a Yahoo e diffuso in video intorno al 2011; traduzione nostra, leggermente condensata ("I do not claim to have invented JSON... I discovered it. It existed in nature."). Il termine Ajax nasce nell'articolo di Garrett "Ajax: A New Approach to Web Applications" (febbraio 2005). fetch è stato standardizzato dal WHATWG; Chrome e Firefox lo supportano dal 2015, Safari dal 2017.

fetch in sei righe

Chiedi, aspetta, controlla, leggi

const BASE = "http://localhost:8000/api/libri";

async function carica() {
  const r = await fetch(BASE);
  if (!r.ok) throw new Error("HTTP " + r.status);
  const libri = await r.json();
  console.log(libri[0].titolo);
}

carica().catch(err => console.error(err));
  • fetch restituisce subito una Promise della risposta.
  • await aspetta senza bloccare la pagina.
  • r.ok è vero per i codici da 200 a 299.
  • r.json() legge il corpo e lo trasforma in oggetti: è anch'essa asincrona.
Paragone con Java: fetch corrisponde a sendAsync, la Promise al CompletableFuture, await a join (ma senza bloccare il thread: JavaScript nel browser ha un solo thread principale, e bloccarlo congelerebbe la pagina). r.json() è asincrona perché il corpo può arrivare dopo gli header. Se il corpo non è JSON valido, r.json() lancia un SyntaxError. Il JSON dell'API diventa un array di oggetti JavaScript: libri[0].titolo, senza nessuna libreria. È il vantaggio di JSON nel browser.

Quiz a trabocchetto

fetch su /api/libri/9999, che risponde 404. Che cosa succede alla Promise?

  1. Viene rifiutata e si finisce nel catch
  2. Resta in attesa per sempre
  3. Si risolve: r.ok è falso e r.status vale 404
  4. Si risolve con null

Per fetch un 404 è una risposta HTTP riuscita: il server ha risposto. La Promise viene rifiutata solo per errori di rete, o quando il CORS blocca la risposta. Per questo bisogna sempre controllare r.ok.

È lo stesso comportamento di HttpClient in Java (lezione 10): 404 e 500 sono risposte, il server spento è un'eccezione. La A è la risposta più scelta, perché axios invece rifiuta la Promise per i codici fuori da 2xx: due librerie, due scelte diverse. Senza il controllo su r.ok, il codice prova a leggere libro.titolo da {"errore": "..."} e mostra "undefined" nella pagina, un bug molto comune.

Al computer · 20 minuti

Il meteo della tua città in una pagina

const url = "https://api.open-meteo.com/v1/forecast" +
  "?latitude=41.90&longitude=12.50&current=temperature_2m,wind_speed_10m";
async function meteo() {
  const r = await fetch(url);
  if (!r.ok) throw new Error("HTTP " + r.status);
  const d = await r.json();
  document.getElementById("t").textContent =
    d.current.temperature_2m + " " + d.current_units.temperature_2m;
}
meteo().catch(e => document.getElementById("t").textContent = e.message);
  1. Crea meteo.html con un <p id="t"> e questo script; aprilo nel browser.
  2. Metti le coordinate della tua città e mostra anche il vento.
Controllo: la pagina mostra un numero seguito da °C, per esempio 17.4 °C, e il vento in km/h. Nella scheda Rete compare una richiesta con stato 200 verso api.open-meteo.com.
Lo script va in fondo al body, dentro <script>. Funziona anche aprendo il file con doppio clic (file://), perché Open-Meteo risponde con Access-Control-Allow-Origin: * e quindi permette le chiamate da qualunque pagina: un ottimo esempio da riprendere quando spieghiamo il CORS. Le unità sono in d.current_units (wind_speed_10m in km/h per default). Verificare prima che il dominio sia raggiungibile dalla rete della scuola. Per i più veloci: aggiungere &daily=temperature_2m_max&timezone=Europe/Rome e mostrare le massime dei prossimi giorni in una lista.

Dal JSON alla pagina

textContent, non innerHTML

Così sì

for (const l of libri) {
  const li = document.createElement("li");
  li.textContent = `${l.titolo} (${l.anno})`;
  ul.append(li);
}

Il titolo resta testo, qualunque carattere contenga.

Così no

for (const l of libri) {
  ul.innerHTML +=
    `<li>${l.titolo}</li>`;
}

Un titolo con <img src=x onerror=…> esegue codice nel browser di chi guarda.

È lo stesso Cross-Site Scripting della JSP (lezione 10), ma lato browser: in quel caso serviva l'escape sul server, qui basta non far interpretare il testo come HTML. Curiosità: un <script> inserito con innerHTML non viene eseguito, ma un <img onerror> sì; per questo l'esempio usa l'immagine. Oltre alla sicurezza, innerHTML += in un ciclo è lento: a ogni giro il browser rianalizza tutto il contenuto della lista. ul.replaceChildren() svuota la lista prima di ridisegnarla.

Same-origin policy e CORS

Il browser protegge l'utente, non il server

Origine = schema + host + porta. Una pagina può leggere liberamente solo le risposte della propria origine.

Pagina su http://localhost:5500 chiama…Stessa origine?
http://localhost:5500/apisì
http://localhost:8000/apino: porta diversa
https://localhost:5500/apino: schema diverso
http://127.0.0.1:5500/apino: host diverso

CORS

Cross-Origin Resource Sharing: il server dichiara con degli header quali altre origini possono leggere le sue risposte. Il browser controlla e decide.

curl e Java non sono browser: il CORS non li riguarda.

Perché esiste: senza same-origin policy, una pagina malevola aperta in un'altra scheda potrebbe chiamare con fetch il sito della tua banca o il registro elettronico, dove sei già autenticato con i cookie, e leggere le risposte. La policy impedisce la lettura. CORS è il modo controllato per allentarla. Il caso 127.0.0.1 sorprende sempre: per il browser localhost e 127.0.0.1 sono nomi diversi, quindi origini diverse. Il CORS non è una protezione del server: chiunque può chiamare l'API con curl. Per proteggere l'API servono autenticazione e autorizzazione.

Mettiti alla prova

La GET bloccata dal CORS: il server l'ha eseguita?

  1. Sì: la richiesta è arrivata e il server ha risposto, ma il browser non passa la risposta allo script
  2. No: il browser non l'ha mai inviata
  3. No: il server l'ha rifiutata con 403
  4. Sì, e lo script riceve una risposta vuota con stato 0

Per una richiesta "semplice", come una GET senza header particolari, il browser la invia e poi controlla gli header CORS della risposta. Se mancano, la blocca prima che arrivi a JavaScript. Per questo il CORS non protegge da GET che cambiano dati: le operazioni con effetti non vanno mai fatte con GET.

La B è vera solo per le richieste che richiedono il preflight (prossima slide): un POST con Content-Type application/json, una PUT, una DELETE. Lì il browser chiede prima il permesso con OPTIONS e, se non lo ottiene, la richiesta vera non parte. La C confonde il CORS con l'autorizzazione: il server non sa nemmeno di "violare" il CORS, risponde 200. La D descrive in parte le risposte "opache" che si ottengono con mode: "no-cors", che non si possono leggere: un dettaglio per i curiosi.

Il server dà il permesso

Quattro header e una risposta a OPTIONS

static void cors(HttpExchange ex) {
  Headers h = ex.getResponseHeaders();
  h.set("Access-Control-Allow-Origin", "*");   // in produzione: l'origine precisa
  h.set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE");
  h.set("Access-Control-Allow-Headers", "Content-Type");
  h.set("Access-Control-Expose-Headers", "Location");
}

// all'inizio di gestisci(), prima di tutto il resto:
cors(ex);
if (ex.getRequestMethod().equals("OPTIONS")) {   // la richiesta di preflight
  ex.sendResponseHeaders(204, -1); ex.close(); return;
}
Gli header vanno su tutte le risposte, anche su quelle d'errore: altrimenti un 404 arriva a JavaScript come "Failed to fetch" e non si capisce più che cosa è successo. Con * qualsiasi sito può leggere le risposte: va bene per un'API pubblica senza dati personali o in sviluppo; per un'API con login si mette l'origine esatta (per esempio https://biblioteca.scuola.it) e, se si usano i cookie, anche Access-Control-Allow-Credentials: true, che non è ammesso insieme a *. Expose-Headers serve per leggere Location da JavaScript (quiz più avanti). Codice provato con Chromium contro il BiblioServer modificato. Dopo la modifica, rieseguire la collezione di test della lezione 11: deve restare tutta verde.

Puzzle

Un POST con JSON da un'altra origine: metti in ordine

  1. Lo script chiama fetch con POST e Content-Type application/json
  2. Il browser invia prima una richiesta OPTIONS con l'header Origin
  3. Il server risponde 204 con gli header Access-Control-Allow-*
  4. Il browser controlla che origine, metodo e header siano ammessi
  5. Il browser invia il vero POST con il JSON
  6. Il server risponde 201 e il browser passa la risposta allo script
Ordine corretto come scritto. Il preflight scatta per i metodi diversi da GET, HEAD e POST, e anche per un POST quando il Content-Type non è uno dei tre "semplici" (text/plain, multipart/form-data, application/x-www-form-urlencoded), o quando ci sono header personalizzati come Authorization. Nella scheda Rete degli strumenti per sviluppatori si vedono entrambe le richieste: OPTIONS e POST. Il browser può ricordare il permesso per un po' se il server invia Access-Control-Max-Age.

Puzzle

Abbina ogni header al suo significato

Origin
Il browser dice da quale origine viene la pagina che chiama
Access-Control-Allow-Origin
Il server dice quale origine può leggere la risposta
Access-Control-Allow-Methods
I metodi ammessi, nella risposta al preflight
Access-Control-Allow-Headers
Gli header che lo script può inviare, come Content-Type
Access-Control-Expose-Headers
Gli header della risposta che lo script può leggere
Lavoro a coppie, 3 minuti. Domanda: quale di questi header lo scrive il browser e quale il server? (Origin lo aggiunge il browser, e lo script non può falsificarlo; tutti gli Access-Control-Allow-* li manda il server.) Con curl invece Origin si può scrivere a mano: un'altra prova che il CORS è una regola dei browser, non una difesa del server.

La biblioteca nel browser: leggi, aggiungi, elimina

const r = await fetch(BASE, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ titolo: d.get("titolo"),
    autore: d.get("autore"), anno: Number(d.get("anno")) })
});
msg.textContent = r.ok ? "Aggiunto: " + r.headers.get("Location")
                       : "Errore " + r.status;
  1. Aggiungi cors() e il ramo OPTIONS al server e riavvialo.
  2. In libri.html: un form con titolo, autore e anno che invia il POST; poi richiama carica().
  3. Accanto a ogni libro un pulsante Elimina con method: "DELETE".
Controllo: la lista mostra i 3 libri. Aggiungendo Lessico famigliare compare Aggiunto: /api/libri/4 e il libro in lista. Nella scheda Rete il POST è preceduto da un OPTIONS con stato 204. Elimina toglie il libro senza ricaricare la pagina.
d è new FormData(e.target) nel gestore dell'evento submit, con e.preventDefault() per non ricaricare la pagina. Number() serve perché i campi di un form sono sempre stringhe: senza, il server riceverebbe "anno":"1963" e la nostra espressione regolare per i numeri non lo troverebbe (risposta 400). Il pulsante: x.onclick = async () => { await fetch(`${BASE}/${l.id}`, { method: "DELETE" }); carica(); }. Soluzione completa provata con Chromium (pagina su localhost:5500, server su 8000). Se compare "Aggiunto: null", manca Access-Control-Expose-Headers: è il quiz successivo.

Quiz per chi ha finito il laboratorio

Il POST risponde 201 con Location, ma r.headers.get("Location") dà null. Perché?

  1. fetch non legge mai gli header della risposta
  2. Bisogna scrivere "location" in minuscolo
  3. Il server ha risposto 201 senza Location
  4. Da un'altra origine lo script legge solo pochi header, se il server non ne espone altri

Con il CORS lo script vede solo gli header "sicuri", come Content-Type. Location è arrivato al browser (si vede nella scheda Rete), ma per leggerlo il server deve aggiungere Access-Control-Expose-Headers: Location.

Provato con Chromium: senza Expose-Headers la pagina mostra "Aggiunto: null", con l'header mostra "Aggiunto: /api/libri/4". La B è sbagliata: headers.get non distingue maiuscole e minuscole. Gli header leggibili per default (CORS-safelisted response headers) sono Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified e Pragma. Con la pagina servita dalla stessa origine dell'API il problema non esiste: un buon motivo, nei progetti, per servire front-end e API dallo stesso dominio.

Oggi

Le risposte dei chatbot arrivano a pezzi con i Server-Sent Events visti nella lezione 5. Con fetch li leggi man mano da response.body: la pagina scrive il testo mentre il modello lo genera.

Lo schema si chiama spesso "backend for frontend" o proxy: è la stessa architettura della JSP della lezione 10, con il server che custodisce il segreto. Il server può anche limitare quante richieste fa ogni utente, per non spendere troppo. Lo streaming: le API dei principali fornitori di modelli supportano il formato Server-Sent Events (Content-Type text/event-stream); in JavaScript si legge con response.body.getReader() oppure, per GET, con EventSource. Non serve mostrare il codice: basta far vedere nella scheda Rete di un chatbot che la risposta arriva in molti pezzi.
