Menti che ci hanno preceduto

Che cosa può dimostrare un test

Per questo i test si pianificano: si sceglie che cosa provare, come, e che cosa ci si aspetta, prima di guardare il risultato.
Originale: "Program testing can be used to show the presence of bugs, but never to show their absence!" (EWD249). Traduzione nostra. Chiedere: allora perché testiamo? Perché ogni bug trovato prima del lancio costa meno di uno trovato dagli utenti.

Al computer · 20 minuti · in squadra

Validatori e link rotti

  1. Apri validator.w3.org/nu, scheda File upload, e carica ogni pagina HTML del sito.
  2. Correggi gli errori dal primo: spesso un errore ne genera altri.
  3. Fai lo stesso per il CSS su jigsaw.w3.org/css-validator.
  4. Crea piano-test.md con una tabella: ID, azione, atteso, ottenuto, esito. Scrivi almeno 10 casi.
Controllo: il validatore HTML risponde "Document checking completed. No errors or warnings to show." per ogni pagina. Nel piano di test ci sono almeno 3 casi sul modulo, inclusi dati sbagliati.
Errori tipici: tag non chiusi, id duplicati, attributi inventati, img senza alt (il validatore lo segnala come errore), elementi nel posto sbagliato (un div dentro un p). Dopo la pubblicazione si può usare il W3C Link Checker (validator.w3.org/checklink) sull'indirizzo pubblico.

Quiz a trabocchetto

Il validatore W3C non trova errori. Quindi il sito…

  1. è accessibile
  2. è ottimizzato per i motori di ricerca
  3. funziona su tutti i browser
  4. ha HTML sintatticamente corretto, e niente di più garantito

Il validatore controlla la grammatica dell'HTML. Un sito valido può avere testi illeggibili, link che portano alla pagina sbagliata, contrasti bassi o una pagina da 10 MB. Validazione, accessibilità, SEO e compatibilità sono test diversi.

È lo stesso ragionamento di Lighthouse 100 nella lezione sull'accessibilità e della compilazione in Java: "compila" non vuol dire "funziona". HTML valido aiuta comunque i browser e le tecnologie assistive a interpretare la pagina in modo prevedibile.

Mettere online

Hosting, dominio, DNS, HTTPS

Hosting

Il server che conserva i file e risponde alle richieste. Statico, condiviso, VPS, cloud.

Dominio

Il nome, come clubalfiere.it. I .it sono gestiti dal Registro .it del CNR di Pisa.

DNS

Collega il nome all'indirizzo IP del server con record A, AAAA, CNAME.

HTTPS

Certificato TLS: cifra il traffico e prova l'identità del sito. Gratuito con Let's Encrypt.

Un sito statico (solo HTML, CSS, immagini) si pubblica gratis e regge molto traffico; un modulo che salva dati richiede un servizio esterno o un server.
Il dominio si registra tramite un registrar (a pagamento, di solito annuale). Collegare un dominio a GitHub Pages: record CNAME per www verso utente.github.io e record A per il dominio nudo verso gli IP indicati da GitHub. Il modulo di iscrizione su un sito statico: servizi di form esterni o un Google Form incorporato (attenzione all'informativa privacy). Collegare all'unità 1: HTTPS protegge il traffico, non rende sicuro il server.

Puzzle

Pubblicare con GitHub Pages: in che ordine?

  1. Crei il repository pubblico sito-squadra
  2. Metti index.html nella radice del repository
  3. Fai commit e push sul branch main
  4. Settings › Pages: sorgente "Deploy from a branch", main, /(root)
  5. Aspetti che il deploy compaia completato in Actions
  6. Apri https://utente.github.io/sito-squadra/
La pagina iniziale deve chiamarsi index.html (minuscolo). Il deploy richiede di solito meno di un minuto e si vede nella scheda Actions ("pages build and deployment"). GitHub Pages è gratuito per i repository pubblici con l'account gratuito. Attenzione: i file del repository pubblico li vede chiunque, quindi niente password o dati personali nel codice.

Al computer · 25 minuti · in squadra

Il vostro sito è online

  1. Nel repository sito-squadra carica le pagine, il CSS e le immagini (pulsante Add file o con Git).
  2. Vai su Settings › Pages e scegli il branch main, cartella /(root), poi Save.
  3. Apri l'indirizzo che compare in cima alla pagina, da PC e da telefono.
  4. Aggiorna nella sitemap gli indirizzi con quello definitivo.
Controllo: l'indirizzo inizia con https://, il browser mostra il lucchetto, le immagini compaiono anche da telefono. Se vedi un 404, controlla il nome index.html e le maiuscole nei percorsi.
GitHub Pages gira su Linux: i percorsi distinguono le maiuscole. "Foto.JPG" in HTML e "foto.jpg" nel repository funziona su Windows in locale ma non online: errore frequentissimo. Alternativa senza Git: Netlify (con account gratuito) permette di trascinare la cartella del sito nella pagina di deploy. Ricordare che sui siti di progetto github.io il robots.txt non è nella radice dell'host (lezione SEO).

Puzzle

Abbina record DNS e codici HTTP

Record A
Nome di dominio → indirizzo IPv4
Record AAAA
Nome di dominio → indirizzo IPv6
Record CNAME
Un nome è un alias di un altro nome
HTTP 301
Risorsa spostata definitivamente
HTTP 404
La risorsa non esiste a questo indirizzo
HTTP 503
Server momentaneamente non disponibile
Ripasso di reti dalla quarta: il DNS lavora a livello applicativo, su UDP porta 53 (TCP per risposte grandi). Domanda aggiuntiva: che codice restituisce un server quando la pagina c'è? 200. E se chiedi di accedere a una pagina riservata senza essere autenticato? 401.

Al computer · 15 minuti

Guarda il tuo sito come lo vede la rete

  1. Apri il Prompt dei comandi e scrivi nslookup utente.github.io (con il nome della squadra).
  2. Annota gli indirizzi IPv4 della risposta.
  3. Scrivi curl -I https://utente.github.io/sito-squadra/
  4. Prova anche una pagina che non esiste e confronta la prima riga.
  5. Salva l'output in rete.txt.
Controllo: nslookup restituisce indirizzi che iniziano con 185.199. (i server di GitHub Pages). curl mostra un codice 200 e una riga server: GitHub.com; la pagina inesistente risponde 404.
curl -I chiede solo le intestazioni (metodo HEAD). Nell'output si vedono anche content-type, last-modified, cache-control, age e x-cache: GitHub Pages serve i file attraverso una rete di distribuzione (CDN). curl è incluso in Windows 10 dalla versione 1803 e in Windows 11. Collegamento con l'unità 2: è la stessa analisi di una risposta HTTP fatta per le API REST.

Mettiti alla prova

Rinomini eventi.html in calendario.html. Che cosa fai?

  1. Niente: Google se ne accorge da solo
  2. Un redirect 301 dal vecchio al nuovo indirizzo, e aggiorni link e sitemap
  3. Lasci online la vecchia pagina, uguale alla nuova
  4. Un redirect 302, così è più veloce

Il vecchio indirizzo è nei preferiti, nei link di altri siti e nell'indice dei motori. Il 301 dice "spostato per sempre": utenti e motori arrivano alla nuova pagina e il posizionamento si trasferisce. Il 302 è per gli spostamenti temporanei; due pagine uguali creano contenuti duplicati.

Approfondimento: GitHub Pages non permette di configurare redirect 301 lato server. Soluzioni: tenere la vecchia pagina con un meta refresh e un link canonical verso la nuova (ripiego accettato), oppure usare un host che supporta i redirect, come Netlify con un file _redirects (riga: /eventi.html /calendario.html 301). La regola migliore resta: scegliere bene gli indirizzi all'inizio e cambiarli il meno possibile.

Aggiornamento

Il giorno dopo il lancio comincia il lavoro vero

1

Contenuti

Chi aggiorna che cosa e quando: calendario mensile, notizie, foto. Niente "Ultime notizie" del 2023.

2

Versioni e backup

Ogni modifica è un commit: si torna indietro in un minuto. Una copia anche fuori da GitHub.

3

Controlli periodici

Link rotti, Lighthouse, scadenza del dominio, statistiche rispettose della privacy.

Con un CMS si aggiungono gli aggiornamenti di sicurezza di software e plugin: un sito abbandonato è un bersaglio.
Statistiche: uno strumento di analytics che usa cookie di profilazione richiede il consenso (linee guida cookie del Garante, 2021); esistono soluzioni senza cookie o con dati anonimizzati. Nel 2022 il Garante italiano ha ritenuto illecito l'uso di Google Analytics da parte di un sito per il trasferimento dei dati negli USA, prima dell'accordo UE-USA del 2023: buon esempio di come le regole cambiano e vanno seguite. Collegare all'unità 1 (CMS e vulnerabilità web).

Una storia vera

19 luglio 2024: un aggiornamento senza prova graduale

Un file di configurazione difettoso del software di sicurezza CrowdStrike arriva a tutti i clienti insieme. Circa 8,5 milioni di computer Windows vanno in crash: aeroporti, ospedali, banche.

Lezione per chiunque pubblichi: prova in un ambiente di test, rilascia a pochi, poi a tutti, e prepara il modo per tornare indietro.

Oggi

Gli agenti AI per il codice possono eseguire validatori, test e Lighthouse a ogni modifica, per esempio con GitHub Actions. Ma decidere se pubblicare, e controllare che cosa hanno cambiato, resta compito vostro.

Il numero di 8,5 milioni è la stima di Microsoft. Il problema era un aggiornamento di contenuti (non del programma) distribuito senza rilascio graduale; CrowdStrike ha poi introdotto rilasci a scaglioni ("canary"). Collegare al deck "Claude Code": un agente può aprire una pull request con le correzioni del validatore, la squadra la rivede prima del merge. Per un sito di squadra il "test environment" può essere un branch o un'anteprima di Netlify.
