Editor

Da Blocco note a un editor di codice

Blocco note

  • c'è su ogni PC Windows
  • salva testo puro: va benissimo per l'HTML
  • nessun aiuto: ogni errore lo trovi da solo

VS Code (gratuito, Microsoft, 2015)

  • colori diversi per tag, attributi e valori
  • completamento: chiude i tag e suggerisce le proprietà
  • Emmet: scrivi ! e premi Tab, compare lo scheletro
  • tutta la cartella del sito in una colonna
Un editor di codice non scrive il codice per te: ti fa vedere prima gli errori. Una virgoletta non chiusa colora di "stringa" tutto il resto della riga.
Se VS Code è installato in laboratorio, mostrarlo alla LIM: aprire la cartella torneo con File › Apri cartella, scrivere ! + Tab in un file nuovo .html, mostrare la colorazione. Emmet è integrato in VS Code. L'estensione Live Server ricarica automaticamente la pagina a ogni salvataggio, ma richiede l'installazione: facoltativa. Alternative leggere: Notepad++ (Windows), o l'editor online di CodePen.

Quiz a trabocchetto

Perché non conviene scrivere l'HTML con Word?

  1. Word non sa salvare file .html
  2. Cambia le virgolette dritte " in virgolette tipografiche “ ” e aggiunge codice suo
  3. Word costa, Blocco note no
  4. L'HTML si può scrivere solo con programmi per programmatori

Il correttore automatico trasforma " in “ ”: per il browser href=“pagina.html” non è più un attributo valido. Inoltre "Salva come pagina web" produce molto codice superfluo. Blocco note invece salva testo puro e va benissimo.

A è falsa (Word salva in HTML, ma con molto codice in più). D è il pregiudizio opposto: qualsiasi editor di testo puro va bene. Lo stesso problema delle virgolette capita copiando codice da un PDF, da una presentazione o da certe chat: se un attributo "non funziona" senza motivo, riscrivere le virgolette a mano.

Ambienti online

CodePen e JSFiddle: il laboratorio nel browser

  • Tre pannelli: HTML, CSS, JavaScript
  • L'anteprima si aggiorna mentre scrivi
  • Si usano senza account e senza installare nulla, anche da un tablet
  • Per salvare e condividere un link serve registrarsi; altrimenti copia il codice nei tuoi file
Ideali per provare un'idea (un menu, un effetto hover). Per un sito di più pagine meglio una cartella sul disco.

Quando usarli

  • fare una prova veloce
  • isolare un errore in poche righe
  • mostrare il problema al docente
  • studiare un esempio trovato online
Gli studenti hanno 16-17 anni: possono registrarsi a questi servizi, ma non è necessario. Se un sito è bloccato dal filtro della scuola, si usa l'altro; in ultima istanza un file .html con un tag style sul disco. "Isolare un errore" è una competenza preziosa: ridurre il codice al minimo che mostra ancora il problema.

Al computer · 15 minuti

Prova lampo in CodePen con Emmet

  1. Apri codepen.io/pen (o jsfiddle.net).
  2. Nel pannello HTML scrivi nav>a*3 e premi Tab: Emmet crea il menu.
  3. Dai un href e un testo ai tre link e la classe attivo al primo.
  4. Nel pannello CSS incolla le regole del menu dal sito del torneo.
  5. Cambia colori e padding finché il menu ti piace, poi copia il CSS nel tuo stile.css.
Controllo: dopo Tab compare <nav> con tre <a href=""></a>. Il menu si aggiorna mentre scrivi, senza salvare né ricaricare. Prova anche ul>li*5 e table>tr*3>td*2.
In CodePen Emmet è attivo di default nei pannelli HTML e CSS; in JSFiddle si usa ugualmente il tasto Tab (se non funziona, scrivere a mano). In VS Code le stesse abbreviazioni funzionano nei file .html. Significato: > = dentro, * = ripeti. Chi finisce: provare h2+p (fratelli) e .carta*3 (tre div con classe carta).

PannelloA che cosa serve
Elementi e Stilivedere l'HTML vero, le regole applicate e quelle barrate, modificarle in diretta

Si aprono con F12 o con tasto destro › Ispeziona. Nel 2006 Joe Hewitt creò Firebug, un'estensione di Firefox; la sua idea piacque così tanto che oggi è integrata in tutti i browser.

I nomi sono quelli di Chrome ed Edge in italiano; in Firefox: Ispettore, Console, Rete, Visualizzazione flessibile. La scheda Rete l'hanno vista nella lezione sul World Wide Web (codici di stato HTTP). Firebug è stato sviluppato dal 2006 e dismesso nel 2017, quando i suoi strumenti erano ormai integrati negli strumenti di sviluppo di Firefox.

Al computer · 15 minuti

Fai il detective sul tuo sito

  1. Apri la home del tuo sito (torneo o mini-sito) e premi F12.
  2. Stili: seleziona un link del menu. Quali regole vedi barrate e perché?
  3. Togli la spunta a float della colonna laterale: che succede?
  4. Modalità dispositivo: scegli un telefono. Il layout regge?
  5. Rinomina per prova stile.css in stile2.css, ricarica con la scheda Rete aperta, poi rimetti il nome giusto.
Controllo: nella scheda Rete la riga di stile.css compare in rosso con stato 404 o con "file non trovato" (aprendo da disco il messaggio cambia a seconda del browser). Sul telefono le due colonne diventano strettissime: lo risolveremo con il responsive nell'Unità 5.
Punto 2: le regole barrate sono quelle sconfitte nella cascata (per esempio il colore di a sovrascritto da nav a); è il modo più rapido per capire la specificità. Punto 5: aprendo il file con file:// non c'è un vero server, quindi Chrome mostra "(failed) net::ERR_FILE_NOT_FOUND" invece di 404; il concetto è lo stesso. Ricordare: le modifiche fatte nei DevTools si perdono ricaricando.

Validatori

Un correttore severo, gratuito, del W3C

HTML: validator.w3.org

Controlla un indirizzo web, un file caricato o il codice incollato.

Error: An img element must have an alt attribute…

Error: Stray end tag div.

CSS: jigsaw.w3.org/css-validator

Controlla un foglio di stile e segnala proprietà e valori inesistenti.

colour: Proprietà inesistente

I messaggi sono in inglese per l'HTML, in italiano per il CSS se il browser è in italiano.

Si parte sempre dal primo errore: spesso un tag non chiuso ne genera altri dieci a cascata.
Traduzione dei messaggi: "Un elemento img deve avere l'attributo alt"; "Tag di chiusura div in più, senza un div aperto". Il messaggio del CSS può avere parole leggermente diverse a seconda della versione del validatore. Il W3C (World Wide Web Consortium), fondato da Tim Berners-Lee nel 1994, scrive gli standard del web; il validatore HTML attuale si chiama "Nu Html Checker".

Al computer · 20 minuti

Zero errori: valida il tuo sito

  1. Apri validator.w3.org, scheda Validate by File Upload, carica index.html e premi Check.
  2. Correggi il primo errore nel tuo file, salva, ricarica il file nel validatore. Ripeti.
  3. Fai lo stesso con le altre pagine.
  4. Apri jigsaw.w3.org/css-validator, scheda Carica file, e controlla stile.css.
  5. Annota quanti errori avevi all'inizio per ogni file e quale era il più frequente.
Controllo: per l'HTML compare "Document checking completed. No errors or warnings to show."; per il CSS "Congratulazioni! Nessun errore trovato." (in inglese "Congratulations! No Error Found."). Gli avvisi (warning) non sono errori, ma leggili.
Errori tipici trovati: alt mancante, tag chiusi nell'ordine sbagliato (<b><i>…</b></i>), id ripetuti, <li> fuori da ul/ol, attributi con virgolette tipografiche, colour al posto di color. Il validatore non vede le immagini caricate separatamente: un percorso sbagliato non è un errore di validazione (lo si trova con la scheda Rete). Se validator.w3.org è lento, si può incollare il codice nella scheda Validate by Direct Input.

Mettiti alla prova

Il validatore dice: zero errori. Quindi la pagina…

  1. è accessibile anche a chi non vede
  2. si vede identica su tutti i browser e i telefoni
  3. è leggera e veloce da caricare
  4. rispetta le regole di scrittura dello standard

Il validatore controlla la sintassi: tag, attributi, annidamenti. Un alt scritto "immagine" è valido ma inutile, un layout può rompersi sul telefono, una foto da 8 MB è valida. Validare è necessario, non sufficiente.

A è il distrattore più forte perché il validatore segnala l'alt mancante: ma non può giudicare se l'alt è utile, né il contrasto dei colori, né l'uso della tastiera. Per questo nell'Unità 5 useremo WAVE e Lighthouse e, soprattutto, i test con persone vere.

Assistenti AI

Un collega veloce che a volte sbaglia con sicurezza

Usali per

  • spiegare un messaggio di errore
  • chiedere perché una regola non funziona
  • avere un esempio da studiare e riscrivere

Non usarli per

  • consegnare codice che non sai spiegare
  • incollare dati personali o password

Oggi

Gli assistenti di programmazione sono dentro gli editor (per esempio GitHub Copilot in VS Code, gratuito per gli studenti verificati) e ormai anche nei DevTools di alcuni browser. Generano codice prevedendo il testo più probabile: per questo possono proporre tag obsoleti, proprietà inventate o un alt vuoto, con lo stesso tono sicuro di quando hanno ragione.

Demo consigliata alla LIM, guidata dal docente (molti chatbot richiedono 13+ con consenso dei genitori o 18+, quindi niente account personali in classe): chiedere a un assistente "scrivi una pagina HTML con il menu del torneo di calcetto" e far revisionare il risultato alla classe con la checklist del validatore. GitHub Copilot è gratuito per gli studenti verificati tramite GitHub Education. In Chrome l'assistenza AI nei DevTools va attivata nelle impostazioni e richiede un account, con limiti di età e di paese: solo dimostrazione. Regola di classe: se usi l'AI, lo dichiari.

Revisione del codice

Un'AI ha scritto queste righe: che cosa non va?

<center>Torneo 3E</center>

Tag obsoleto

center non fa più parte dell'HTML: la centratura si fa nel CSS con text-align: center.

<img src="campo.jpg" alt="">

È la foto della finale.

alt vuoto su un'immagine importante

Il validatore non protesta, ma chi usa uno screen reader perde l'informazione.

p { color: #cccccc; }

Testo su sfondo bianco.

Contrasto troppo basso

Grigio chiaro su bianco si legge male: valido per il W3C, faticoso per le persone.

Tre errori che un validatore trova solo in parte: il primo sì (center è obsoleto, il Nu Html Checker lo segnala come errore), il secondo e il terzo no. alt="" è corretto solo per le immagini decorative. Il contrasto si verifica con gli strumenti dell'Unità 5. Far votare prima di girare ogni carta.

Menti che ci hanno preceduto

Scrivere è facile, capire è il lavoro

Oggi

Se il codice lo scrive un'AI, la parte difficile resta tutta a te: leggerlo, capirlo, trovarne gli errori. Codice semplice e ordinato aiuta te, i tuoi compagni e anche l'AI a cui chiederai aiuto la prossima volta.

Traduzione nostra da: "Everyone knows that debugging is twice as hard as writing a program in the first place. So if you're as clever as you can be when you write it, how will you ever debug it?" (B. W. Kernighan e P. J. Plauger, The Elements of Programming Style, 2ª edizione, 1978, cap. 2). Kernighan ha lavorato ai Bell Labs con Ritchie e Thompson, gli autori di Unix (Unità 6). Discussione: che cosa vuol dire codice "astuto" in HTML e CSS? Selettori lunghissimi, trucchi difficili da capire, classi con nomi criptici.

Puzzle

La pagina non funziona: in che ordine procedi?

  1. Salvo il file e ricarico con Ctrl+F5
  2. Apro i DevTools e guardo Console e Rete
  3. Ispeziono l'elemento e cerco le regole barrate
  4. Passo il file al validatore e correggo il primo errore
  5. Isolo il problema in poche righe su CodePen
  6. Chiedo aiuto (compagno, docente o AI) mostrando quelle righe
Ordine consigliato, non l'unico possibile: l'importante è partire dalle verifiche più veloci (ho salvato? il file si carica?) e chiedere aiuto con un esempio minimo. Un esempio minimo è il modo migliore per ottenere una risposta utile da chiunque, AI compresa.
