Unità 3 · Applicazioni Java per la comunicazione in rete

WebSocket:
la chat nel browser

HTTP sa solo rispondere. Con una richiesta speciale la connessione cambia protocollo e diventa un canale sempre aperto, in cui anche il server può parlare per primo.

Lezione di laboratorio, 3-4 ore. Obiettivi: capire il limite di HTTP (richiesta-risposta) e le alternative (polling, long polling, Server-Sent Events, WebSocket); leggere l'handshake di RFC 6455 e calcolare Sec-WebSocket-Accept; conoscere i frame; usare l'API WebSocket del browser; scrivere un endpoint con jakarta.websocket su Tomcat 10.1. Preparare prima: Apache Tomcat 10.1 (zip, nessuna installazione), JDK 21 con JAVA_HOME impostata, browser con DevTools. Se Tomcat non si può usare, c'è un server alternativo solo JDK (vedi note del secondo laboratorio).

Per cominciare

Quale app "in tempo reale" usi di più?

  1. Un gioco multiplayer
  2. Un documento condiviso con i compagni
  3. Una chat o Discord
  4. Risultati sportivi in diretta
  5. Un chatbot che scrive la risposta poco alla volta
Tutte e cinque hanno lo stesso bisogno: il server deve mandare dati al browser SENZA che il browser li abbia appena chiesti. Chiedere: come fa Google Docs a mostrarti il cursore del compagno che scrive? La lezione risponde a questa domanda.

Il problema

In HTTP parla sempre prima il browser

TecnicaCome funzionaDirezioneQuando usarla
PollingIl browser chiede "novità?" ogni N secondibrowser → serverAggiornamenti rari, semplicità
Long pollingIl server tiene la richiesta aperta finché ha una novitàbrowser → serverVecchi sistemi, compatibilità
Server-Sent EventsUna risposta HTTP che non finisce mai: text/event-streamsolo server → browserNotifiche, streaming di testo
WebSocketLa connessione TCP cambia protocollo e resta apertanei due sensiChat, giochi, collaborazione
Con il polling ogni 2 secondi, 1000 utenti fanno 500 richieste al secondo anche quando non succede nulla, e un messaggio arriva in media con 1 secondo di ritardo. SSE è più semplice di WebSocket (è HTTP normale, si riconnette da solo) ma va in una sola direzione: il browser per scrivere fa normali richieste POST. WebSocket è bidirezionale con un overhead minimo per messaggio (pochi byte di intestazione invece di centinaia di header HTTP).

Mettiti alla prova

HTTP/1.1 classico: il server ha un messaggio nuovo per te. Come te lo manda?

  1. Invia una risposta HTTP anche senza richiesta
  2. Lo scrive in un cookie
  3. Non può: deve aspettare che il browser chieda
  4. Con un redirect 302 verso la pagina nuova

In HTTP una risposta esiste solo come risposta a una richiesta. Cookie e redirect viaggiano anch'essi dentro risposte. Per questo servono polling, long polling, SSE o WebSocket.

La A è il tranello: tecnicamente il server ha un socket aperto (con keep-alive) e potrebbe scriverci, ma il browser scarterebbe dati che non corrispondono a una richiesta. HTTP/2 aveva il "server push", ma serviva a inviare in anticipo file (CSS, JS), non messaggi all'applicazione, e i browser principali l'hanno poi disattivato.

RFC 6455 · L'handshake

Una richiesta HTTP che chiede di cambiare protocollo

browser → server
GET /chat/ws HTTP/1.1
Host: localhost:8080
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key:
  dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: http://localhost:8080
server → browser
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept:
  s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

da qui in poi: frame WebSocket
sulla stessa connessione TCP

Il server dimostra di aver capito la richiesta: Accept = Base64( SHA-1( Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )

La chiave e la risposta sono l'esempio ufficiale della RFC 6455 (dicembre 2011, sezione 1.3). La chiave sono 16 byte casuali in Base64, nuovi a ogni connessione. La stringa fissa (un GUID) è scritta nella RFC. Lo scopo NON è la sicurezza: è impedire che un server HTTP qualunque, o una cache, accetti per errore una connessione WebSocket. 101 è un codice informativo (1xx). L'header Origin permette al server di rifiutare pagine di altri siti: un controllo che un server vero deve fare.

Al computer · 15 minuti

Calcola Sec-WebSocket-Accept

Crea AcceptKey.java nella cartella u3-websocket:

static String accept(String key) throws Exception {
    String guid = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11";
    byte[] sha1 = MessageDigest.getInstance("SHA-1")
        .digest((key + guid).getBytes(UTF_8));
    return Base64.getEncoder().encodeToString(sha1);
}

Nel main stampa accept("dGhlIHNhbXBsZSBub25jZQ=="), poi prova una chiave a tua scelta.

Controllo: deve uscire esattamente s3pPLMBiTxaQ9kYGzzhZRbK+xOo=, la risposta dell'esempio della RFC 6455. Un solo carattere diverso nella stringa fissa cambia tutto il risultato.
Import: java.security.MessageDigest, java.util.Base64, static java.nio.charset.StandardCharsets.UTF_8. Si esegue con java AcceptKey.java. Far notare che SHA-1 non è più considerato sicuro per le firme digitali, ma qui non serve sicurezza: serve solo una trasformazione che un server "per caso" non farebbe. Errore tipico: fare la Base64 della stringa esadecimale dell'hash invece che dei 20 byte.

Dopo il 101

Niente più header: piccoli frame nei due sensi

2-14 byte di intestazione

FIN, un opcode (che tipo di frame è), la lunghezza e, dal browser, una maschera di 4 byte.

Testo o binario

Un messaggio può essere testo UTF-8 (per esempio JSON) o dati binari (immagini, audio, stato di un gioco).

Controllo

Close per chiudere con un codice, ping e pong per controllare che l'altro capo sia ancora vivo.

ws:// usa la porta 80 ed è in chiaro; wss:// usa la 443 dentro TLS. Fuori dal laboratorio si usa sempre wss://.
Il ping e pong di WebSocket è un parente del ping ICMP della prima lezione dell'unità: risolve lo stesso problema visto nella chat TCP (accorgersi che l'altro capo è sparito senza chiudere). I browser rispondono da soli ai ping del server; l'API JavaScript non permette di mandarli. La maschera, obbligatoria da client a server, si vede nel quiz. Codici di chiusura comuni: 1000 normale, 1001 pagina chiusa, 1006 connessione persa senza frame di chiusura (non viene mai inviato davvero, lo riporta l'API).

Puzzle

Abbina ogni opcode al suo frame

0x1
Frame di testo UTF-8
0x2
Frame binario
0x8
Chiusura, con un codice come 1000
0x9
Ping: "ci sei ancora?"
0xA
Pong: la risposta al ping
Opcode da RFC 6455, sezione 5.2. Esiste anche 0x0, "continuazione", per un messaggio spezzato in più frame (FIN = 0 su tutti tranne l'ultimo). Il primo byte di un frame di testo completo è 0x81: bit FIN a 1 e opcode 1. Lo si vede nel server alternativo solo JDK delle note.

Il codice · browser

L'API WebSocket in JavaScript

// stesso host e cartella della pagina: ws://localhost:8080/chat/ws
const base = location.pathname.replace(/[^/]*$/, "");
const ws = new WebSocket((location.protocol === "https:" ? "wss://" : "ws://") + location.host + base + "ws");

ws.onopen = () => stato.textContent = "Connesso";
ws.onclose = (e) => stato.textContent = "Disconnesso (codice " + e.code + ")";
ws.onmessage = (e) => {
  const li = document.createElement("li");
  li.textContent = e.data;                   // mai innerHTML: niente XSS
  lista.append(li);
};
modulo.onsubmit = (ev) => {
  ev.preventDefault();
  ws.send(nick.value + ": " + testo.value);
  testo.value = "";
};
Pagina completa index.html (nel compito c'è la stessa struttura): h1, p#stato, ul#lista, form#modulo con input#nick, input#testo e un button; lo script in fondo al body, con const stato = document.getElementById("stato") ecc. Quattro eventi da ricordare: open, message, close, error; un metodo per inviare (send) e uno per chiudere (close). L'URL è costruito dalla pagina stessa, così funziona sia su Tomcat (/chat/ws) sia con il server alternativo (/ws). textContent: se un utente manda <img src=x onerror=alert(1)> deve comparire come testo, non essere eseguito (XSS, Unità 1). Le connessioni sono bloccate se la pagina è in https e il server in ws:// (contenuto misto).

Il codice · server

Un endpoint jakarta.websocket su Tomcat

@ServerEndpoint("/ws")
public class ChatEndpoint {
    private static final Set<Session> sessioni = ConcurrentHashMap.newKeySet();

    @OnOpen  public void apri(Session s)   { sessioni.add(s); }
    @OnClose public void chiudi(Session s) { sessioni.remove(s); }
    @OnError public void errore(Session s, Throwable t) { sessioni.remove(s); }

    @OnMessage
    public void messaggio(String testo, Session da) {
        for (Session s : sessioni) {
            if (!s.isOpen()) continue;
            try {
                synchronized (s) { s.getBasicRemote().sendText(testo); }   // un invio alla volta
            } catch (IOException e) { sessioni.remove(s); }
        }
    }
}
Import: jakarta.websocket.*, jakarta.websocket.server.ServerEndpoint, java.io.IOException, java.util.Set, java.util.concurrent.ConcurrentHashMap. Confronto con la chat TCP: Tomcat fa da solo handshake, frame, maschera e thread; noi scriviamo solo che cosa fare quando si apre, arriva un messaggio, si chiude. Session ha lo stesso ruolo del nostro GestoreClient. Il Set è static perché Tomcat crea un'istanza di ChatEndpoint per ogni connessione. synchronized(s): l'API non permette due invii contemporanei sulla stessa sessione (Tomcat lancia IllegalStateException), e due messaggi possono arrivare insieme da due utenti diversi.

Quiz a trabocchetto

I frame dal browser al server sono "mascherati" con 4 byte casuali. Perché?

  1. Per cifrare i messaggi
  2. Perché proxy e cache lungo la strada non li scambino per richieste HTTP
  3. Per comprimerli
  4. Per dimostrare l'identità dell'utente

La maschera è un semplice XOR con una chiave scritta nel frame stesso: chiunque la toglie. Serve contro attacchi di "cache poisoning": senza, una pagina malevola potrebbe scrivere byte che un vecchio proxy interpreta come una richiesta HTTP. La riservatezza la dà solo wss://.

È il malinteso più diffuso: "mascherato" non vuol dire "cifrato". RFC 6455, sezione 10.3, spiega la motivazione (attacchi alle infrastrutture intermedie, dimostrati da ricercatori mentre lo standard era in preparazione). Il server NON maschera i suoi frame verso il browser. Se in DevTools vedi i messaggi in chiaro è perché il browser li mostra già decodificati.

Se il messaggio compare in grassetto, lo script usa innerHTML: è una vulnerabilità XSS, da correggere con textContent. Estensione: mandare dal server, ogni 10 secondi, un messaggio "ora: hh:mm:ss" a tutti (in ChatEndpoint con un ScheduledExecutorService statico) e osservarlo arrivare senza che il browser abbia chiesto nulla.

Menti che ci hanno preceduto

Il Web non era nato per il tempo reale

2008 → 2011

Il Web era fatto per documenti. Gli sviluppatori inventarono trucchi come il long polling; nel 2008 Ian Hickson e Michael Carter proposero il nome WebSocket; nel 2011 l'IETF pubblicò la RFC 6455.

Originale: "The best way to predict the future is to invent it." Alan Kay la racconta come risposta data nel 1971 in una riunione al PARC con i dirigenti Xerox che chiedevano previsioni sul futuro; traduzione nostra. Kay è uno dei padri della programmazione a oggetti (Smalltalk) e delle interfacce grafiche. La RFC 6455 è di dicembre 2011 (autori Ian Fette e Alexey Melnikov); l'API JavaScript è standardizzata dal WHATWG. Messaggio: molte tecnologie nascono da sviluppatori che "aggirano" i limiti di quelle esistenti.

Il tempo reale oggi

Dalla chat all'intelligenza artificiale

Oggi

Le risposte che "si scrivono da sole"

Quando un chatbot mostra la risposta parola per parola, il server del modello la manda in streaming: le API dei grandi modelli linguistici usano di solito i Server-Sent Events, perché il flusso va solo dal server al client. Le API vocali in tempo reale usano invece WebSocket o WebRTC, perché l'audio va nei due sensi.

Oggi

Collaborare e giocare

Negli editor condivisi come Figma o Google Docs ogni cursore, ogni lettera e ogni forma spostata è un piccolo messaggio inviato al server e inoltrato agli altri, proprio come nel nostro ChatEndpoint. Lo stesso vale per i giochi multiplayer nel browser.

Esempio concreto: con le API di Anthropic o OpenAI, impostando "stream": true la risposta arriva come text/event-stream, con eventi che contengono pezzi di testo (token). Anche il Model Context Protocol (MCP), con cui gli assistenti AI si collegano a strumenti esterni, prevede un trasporto via HTTP che può usare SSE per i messaggi dal server. Figma ha descritto pubblicamente (2019) che i client del suo "multiplayer" si collegano ai server con WebSocket. Domanda: per un chatbot testuale, SSE o WebSocket? SSE basta: la domanda parte con una normale POST, la risposta arriva in streaming.

Puzzle

Metti in ordine la vita di una connessione WebSocket

  1. Il browser scarica la pagina con una normale richiesta HTTP
  2. Lo script esegue new WebSocket(url)
  3. Parte una GET con Upgrade: websocket e la chiave
  4. Il server risponde 101 con Sec-WebSocket-Accept
  5. Client e server si scambiano frame nei due sensi
  6. Uno dei due manda un frame di chiusura con il codice 1000
Domanda: dove avviene l'handshake TCP (SYN, SYN-ACK, ACK)? Prima del passo 3, perché la GET viaggia su una connessione TCP già aperta. Dopo il frame di chiusura l'altro capo risponde con il suo frame di chiusura e poi si chiude la connessione TCP. Far disegnare la stessa sequenza come diagramma: è un ottimo esercizio da esame.

In una prova di progetto la risposta "uso WebSocket" vale poco da sola: vale il perché, confrontato con almeno un'alternativa.
Ricordare anche gli aspetti di sicurezza da citare: wss:// (TLS), controllo dell'header Origin, autenticazione (per esempio un token verificato all'apertura), validazione dei messaggi ricevuti, textContent lato browser. Riepilogo

Cosa portiamo a casa

  • HTTP: parla prima il browser. Polling, SSE e WebSocket aggirano il limite
  • Handshake: GET con Upgrade, risposta 101, Accept da SHA-1 e Base64
  • Poi frame piccoli: testo, binario, close, ping e pong
  • Browser: new WebSocket, onmessage, send, sempre textContent
  • Tomcat: @ServerEndpoint, @OnOpen, @OnMessage, @OnClose
  • Maschera ≠ cifratura: fuori dal lab sempre wss://
