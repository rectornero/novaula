Testare le API
con curl e Postman

Un'API funziona quando risponde bene anche alle richieste sbagliate. Oggi BiblioAPI finisce sotto esame: a mano, con una collezione di test e con uno script.

5G TPSIcurl, Postman e Bruno, test automatici, casi negativi, OpenAPI

Obiettivi: usare curl con le opzioni principali e leggerne l'output verboso; organizzare le richieste in una collezione con variabili e test automatici (Postman o Bruno); progettare casi di test positivi e negativi; automatizzare i controlli con uno script; conoscere OpenAPI come documentazione e contratto. Durata indicativa: 3-4 ore. Software: curl (incluso in Windows 10 e 11); Bruno (desktop, open source, nessun account, le collezioni sono file in una cartella) oppure Postman (desktop; senza account offre un client leggero per le singole richieste, per collezioni e ambienti salvati serve l'accesso: verificare la versione installata in laboratorio). Hoppscotch (hoppscotch.io) funziona dal browser ma per chiamare localhost ha bisogno della sua estensione o dell'app desktop. Serve il BiblioServer della lezione 9 sulla porta 8000.

Puzzle

Abbina ogni opzione di curl a ciò che fa

-i
Mostra anche riga di stato e header della risposta
-v
Mostra tutto lo scambio: richiesta inviata e risposta
-X DELETE
Sceglie il metodo HTTP
-H "Accept: …"
Aggiunge un header alla richiesta
-d @libro.json
Invia come corpo il contenuto di un file
-w "%{http_code}"
Stampa il codice di stato alla fine
Altre opzioni utili: -s (silenzioso, niente barra di avanzamento), -o file (salva il corpo), -L (segue i redirect), --json '{...}' nelle versioni recenti di curl (dalla 7.82) imposta POST, Content-Type e Accept application/json in un colpo solo. La documentazione completa: curl --help all oppure curl.se/docs/manpage.html. curl è nato nel 1998, lo mantiene lo svedese Daniel Stenberg ed è installato in miliardi di dispositivi, dalle auto agli smartphone.

Leggere curl -v

Asterisco, maggiore, minore

* Connected to localhost (127.0.0.1) port 8000

> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/1.1 200 OK

< Content-length: 75
<
{"id":2,"titolo":"Il barone rampante",…}
  • * informazioni di curl: DNS, connessione TCP, TLS.
  • > righe inviate: la richiesta.
  • < righe ricevute: la risposta.
  • La riga vuota separa gli header dal corpo.
  • Content-length: 75 sono byte, non caratteri.
Output reale di curl 8.5 contro il BiblioServer della lezione 9 (le righe sulla barra di avanzamento sono state tolte). È la stessa struttura del messaggio HTTP vista nella lezione 5. Con un URL https le righe con * mostrano anche la negoziazione TLS e il certificato del server: è un ottimo strumento di diagnosi. Domanda: chi ha aggiunto l'header Host? (curl, da solo: in HTTP/1.1 è obbligatorio, e permette a un server con un solo IP di ospitare molti siti.)

Al computer · 20 minuti

Un giro completo di BiblioAPI con curl

curl -i http://localhost:8000/api/libri
curl -i -X POST -H "Content-Type: application/json" -d @libro.json http://localhost:8000/api/libri
curl -i -X PUT -H "Content-Type: application/json" -d @libro2.json http://localhost:8000/api/libri/4
curl -v -X DELETE http://localhost:8000/api/libri/4
  1. Riavvia BiblioServer: i dati tornano ai tre libri iniziali.
  2. Prepara libro.json e libro2.json (stesso libro, anno diverso).
  3. Esegui i comandi e salva l'output in giro-curl.txt, aggiungendo >> giro-curl.txt 2>&1.
Controllo: 200, poi 201 con Location: /api/libri/4, poi 200 con l'anno nuovo, poi < HTTP/1.1 204 No Content senza corpo.
In PowerShell usare curl.exe. Il reindirizzamento 2>&1 serve perché curl scrive l'output di -v sullo standard error, non sullo standard output: senza, nel file finirebbe solo il corpo. Se il POST risponde 400, il JSON nel file è sbagliato: controllare virgolette e virgole (un buon trucco è aprirlo nel browser o in VS Code, che segnala gli errori). Se risponde con un id diverso da 4, il server non è stato riavviato.

Quiz a trabocchetto

curl con -d @libro.json ma senza -X: che cosa parte verso BiblioAPI?

  1. Una GET con il file nella query string
  2. Un POST con Content-Type application/json
  3. Un POST con Content-Type application/x-www-form-urlencoded
  4. Un errore: senza -X curl non sa che metodo usare

Con -d curl passa da solo al metodo POST, ma dichiara il corpo come dati di un modulo HTML. Il nostro server non controlla il tipo e funziona lo stesso; un'API più severa risponderebbe 415 Unsupported Media Type. Per il JSON serve -H "Content-Type: application/json".

Verificato con curl -v: compare "> Content-Type: application/x-www-form-urlencoded". La B è il tranello: il file si chiama .json, ma curl non guarda l'estensione. Conseguenza pratica: un test che "passa" con curl può fallire con un client vero, o viceversa. Se il server controlla il Content-Type (miglioria proposta nella lezione 9), questo diventa un buon caso negativo da aggiungere alla collezione. Con -d e senza -X, aggiungere -X POST è inutile: curl stesso lo segnala in modalità verbosa.

Test automatici

Stesso test, due strumenti

Postman · scheda Scripts, Post-response

pm.test("201 Created", () =>
  pm.response.to.have.status(201));
pm.test("ha un id numerico", () => {
  const libro = pm.response.json();
  pm.expect(libro.id).to.be.a("number");
  pm.collectionVariables.set("id", libro.id);
});

Bruno · scheda Tests

test("201 Created", () => {
  expect(res.getStatus()).to.equal(201);
});
test("ha un id numerico", () => {
  const libro = res.getBody();
  expect(libro.id).to.be.a("number");
  bru.setVar("id", libro.id);
});

Il test salva l'id del libro creato: la richiesta successiva usa {{base}}/libri/{{id}}.

Entrambi usano JavaScript e le asserzioni in stile Chai (expect(...).to.equal, to.be.a, to.have.property). Nelle versioni meno recenti di Postman la scheda si chiamava "Tests"; nelle attuali è in Scripts, Post-response. In Bruno esiste anche la scheda Assert, dichiarativa: res.status eq 201, senza scrivere codice. Concatenare le richieste salvando l'id rende la collezione indipendente dai dati: non serve sapere in anticipo che il nuovo libro avrà id 4.

Al computer · 35 minuti

La collezione di test di BiblioAPI

  1. In Bruno (o Postman) crea la collezione BiblioAPI e un ambiente locale con base = http://localhost:8000/api.
  2. Aggiungi in ordine: elenco, POST nuovo libro, GET {{id}}, PUT {{id}}, DELETE {{id}}, GET {{id}}.
  3. Ogni richiesta ha almeno un test sul codice; il POST salva id.
  4. Avvia il Runner sull'intera collezione, due volte di fila.
  5. Esporta la collezione (in Bruno: la cartella in zip).
Controllo: 6 richieste, tutte verdi, anche alla seconda esecuzione: 200, 201, 200, 200, 204, 404. Se la seconda volta qualcosa fallisce, un test dipende da un id scritto a mano.
L'ultima GET deve aspettarsi 404: è un test positivo di un caso negativo (il libro cancellato non c'è più). Errore tipico: scrivere l'id 4 a mano; alla seconda esecuzione il POST crea il 5 e i test successivi falliscono o, peggio, passano su un altro libro. In Postman l'esportazione è Collection v2.1 in JSON; in Bruno basta comprimere la cartella della collezione. Conservare tutto: è la base del compito per casa e servirà nella lezione 12 per verificare di non aver rotto niente aggiungendo il CORS.

Puzzle

Metti in ordine la collezione: perché ogni test regga da solo

  1. POST /libri e salva l'id ricevuto
  2. GET /libri/{{id}}: il libro esiste e ha il titolo inviato
  3. PUT /libri/{{id}} con l'anno cambiato
  4. GET /libri/{{id}}: l'anno è quello nuovo
  5. DELETE /libri/{{id}}: 204
  6. GET /libri/{{id}}: 404
Ordine corretto come scritto. È lo schema "crea, leggi, modifica, rileggi, cancella, verifica" e lascia il server com'era all'inizio: per questo la collezione si può rieseguire all'infinito. Domanda: perché rileggere dopo il PUT, se il PUT ha già risposto con il JSON aggiornato? (Perché la risposta del PUT dice che cosa il server crede di aver salvato; la GET successiva verifica che lo abbia salvato davvero.)

I casi negativi

Le richieste sbagliate che un'API deve reggere

RichiestaChe cosa simulaAtteso
GET /api/libri/9999Un id che non esiste404
GET /api/libri/abcUn id che non è un numero400
POST /api/libri {"titolo":"X"}Campi obbligatori mancanti400
POST /api/libri {"titolo": JSON non valido400
PATCH /api/libriUn metodo non previsto405
GET /api/autoriUna risorsa che non esiste404

In ogni caso il server deve restare acceso e rispondere con un JSON d'errore: mai un 500, mai uno stack trace.

Il BiblioServer della lezione 9 supera tutti questi casi tranne, a seconda di com'è scritto, GET /api/autori: non c'è un contesto registrato, quindi il JDK risponde 404 con una pagina HTML e non con JSON. Si può correggere registrando un contesto "/" che risponde sempre 404 in JSON. Uno stack trace nella risposta è anche un problema di sicurezza: rivela classi, versioni e percorsi a un attaccante (Unità 1, OWASP: Security Misconfiguration). Un caso in più per i curiosi: un titolo lunghissimo, di centomila caratteri. Che cosa dovrebbe fare il server? (Rifiutarlo con 400 o 413 Content Too Large.)

Mettiti alla prova

Tutti i test della collezione sono verdi. Che cosa sappiamo davvero?

  1. Che l'API si comporta come atteso nei casi che abbiamo provato
  2. Che l'API non ha bug
  3. Che l'API è sicura
  4. Che l'API regge mille utenti insieme

Un test controlla solo ciò che descrive. I bug possono stare nei casi non provati; la sicurezza e il carico richiedono test diversi, come le scansioni di vulnerabilità e i test di carico.

Introduce la citazione di Dijkstra nella slide successiva. Per il carico esistono strumenti come k6 o JMeter; per la sicurezza scanner come OWASP ZAP, da usare solo su sistemi propri o autorizzati. Anche la copertura dei test (quante righe di codice vengono eseguite) dice quanto si è provato, non quanto il codice sia corretto.

Al computer · 20 minuti

Uno script che controlla tutto in un secondo

@echo off
rem test-api.bat: in un file .bat il % si scrive %%
set B=http://localhost:8000/api/libri
curl -s -o NUL -w "GET elenco      %%{http_code}\n" %B%
curl -s -o NUL -w "POST nuovo      %%{http_code}\n" ^
  -X POST -H "Content-Type: application/json" -d @libro.json %B%
curl -s -o NUL -w "GET 4           %%{http_code}\n" %B%/4
curl -s -o NUL -w "DELETE 4        %%{http_code}\n" -X DELETE %B%/4
curl -s -o NUL -w "GET 4 di nuovo  %%{http_code}\n" %B%/4
curl -s -o NUL -w "POST senza dati %%{http_code}\n" -X POST -d "{}" %B%
curl -s -o NUL -w "PATCH elenco    %%{http_code}\n" -X PATCH %B%
  1. Salva test-api.bat accanto a libro.json.
  2. Riavvia il server ed esegui lo script.
  3. Aggiungi due casi negativi della tabella.
Controllo: a server appena avviato: 200, 201, 200, 204, 404, 400, 405, uno per riga.
Output verificato con il BiblioServer della lezione 9. -o NUL butta via il corpo (su Linux e macOS -o /dev/null, e nello script .sh il % non va raddoppiato); -w stampa il codice. Il ^ a fine riga continua il comando sulla riga successiva nel Prompt dei comandi. Lo script dipende dall'id 4, quindi va eseguito a server appena riavviato: è proprio il limite che la collezione con {{id}} risolve. Miglioria: confrontare automaticamente con i codici attesi e stampare OK o ERRORE (in batch con if, oppure riscrivendo lo script in Java con HttpClient o in Python). In azienda questi controlli girano a ogni modifica del codice, in una pipeline di integrazione continua; con Postman c'è Newman, con Bruno il comando bru run (entrambi richiedono Node.js).

Il contratto dell'API

OpenAPI: la documentazione che le macchine sanno leggere

openapi: 3.1.0
info: { title: BiblioAPI, version: "1.0" }
paths:
  /api/libri/{id}:
    get:
      summary: Legge un libro
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer }
      responses:
        "200": { description: Il libro }
        "404": { description: Libro non trovato }

Da un file OpenAPI si generano una pagina di documentazione interattiva, una collezione per Postman o Bruno e perfino il codice dei client.

Oggi

Gli agenti AI usano descrizioni come questa per capire quali operazioni esistono e con quali parametri chiamarle. Un'API ben documentata è un'API che anche un agente sa usare, e sbaglia meno.

OpenAPI nasce dalla specifica Swagger (2011), donata nel 2015 alla OpenAPI Initiative della Linux Foundation; la 3.1 è del 2021. Swagger UI è lo strumento più noto per la documentazione interattiva. Con un file OpenAPI i test possono diventare "test di contratto": si verifica che le risposte reali rispettino lo schema dichiarato. Nella prova d'esame, scrivere gli endpoint in forma tabellare con metodo, URI, parametri e codici è l'equivalente "su carta" di questo file. Per i curiosi: la versione completa di BiblioAPI in OpenAPI è un ottimo esercizio extra del compito.

Sfida a squadre

Il lucchetto del tester

  • 1ª cifra: la prima cifra del codice per GET di un libro cancellato
  • 2ª e 3ª cifra: le ultime due cifre del codice per PATCH su /api/libri
  • 4ª cifra: quante richieste ha la catena del puzzle, prima della DELETE
Aperto! 404, 405 Method Not Allowed, e quattro richieste prima della DELETE: POST, GET, PUT, GET.
Codice: 4054 (4 da 404; 05 da 405; 4 richieste prima della DELETE nella catena: POST, GET, PUT, GET). La quarta cifra fa rileggere il puzzle: alcuni contano anche la DELETE (5) o tutta la catena (6).

Biglietto d'uscita

Completa prima di uscire

L'opzione di curl che mostra anche la richiesta inviata è .

Con -d e senza -X, curl usa il metodo .

Un metodo non previsto sulla risorsa deve ricevere .

Il formato standard per descrivere un'API REST si chiama .
