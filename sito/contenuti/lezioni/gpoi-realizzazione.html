GPOI · Unità 6

La realizzazione

Dalle richieste della coordinatrice al codice che gira: requisiti, interfaccia, specifiche, componenti, database, metriche. E un occhio sempre sul piano.

Obiettivi: scrivere requisiti utente verificabili e distinguere funzionali e non funzionali; progettare l'interfaccia per gli utenti reali; passare dai requisiti alle specifiche; scegliere componenti e linguaggi; progettare il database; misurare il software e monitorare l'avanzamento con il valore guadagnato. Durata: 4 ore (due laboratori). È la fase più lunga del progetto NQ (settimane 5-8). Per lo sviluppo vero si lavora in compresenza con informatica e TPSIT; qui si guarda il progetto con gli occhi di chi lo gestisce.

Chi dovrebbe decidere come è fatta l'interfaccia?

  1. Chi la programma
  2. La coordinatrice, che è il committente
  3. I volontari, provandola

2 minuti. Non c'è una risposta sola: chi programma conosce i limiti tecnici, la committente approva, ma la prova decisiva la fanno gli utenti (Giuseppe, Sara, Marta delle personas). Il PM garantisce che la decisione arrivi in tempo. Ritornare su questo dopo il laboratorio sul prototipo.

Dividi in categorie

Funzionale o non funzionale?

Funzionale: che cosa fa

  • Iscriversi a un turno
  • Cancellare l'iscrizione
  • Esportare gli iscritti in CSV
  • Promemoria il giorno prima

Non funzionale: come lo fa

  • Pagina aperta in meno di 2 s
  • Caratteri grandi e contrasto alto
  • Password salvate con hash
  • Funziona su Chrome, Firefox e Safari
Soluzione nell'ordine scritto. I requisiti non funzionali riguardano prestazioni, usabilità e accessibilità, sicurezza, compatibilità: corrispondono alle caratteristiche di qualità che vedremo con la ISO/IEC 25010. Errore comune: considerare "password salvate con hash" funzionale perché "fa qualcosa"; in realtà descrive come il sistema protegge i dati.

Quiz a trabocchetto

"L'app deve essere facile da usare." Questo requisito è…

  1. Un buon requisito non funzionale, pronto da approvare
  2. Un requisito funzionale
  3. Un desiderio da rendere verificabile, per esempio con un test su utenti reali
  4. Inutile: ogni app deve essere facile

È non funzionale, ma così com'è nessuno può verificarlo. Versione verificabile: "4 volontari su 5 con più di 65 anni si iscrivono a un turno da soli, in meno di 2 minuti, al primo tentativo".

La A è il tranello: la categoria è giusta, ma il requisito non si può collaudare. Collegare all'obiettivo SMART del charter: lo stesso principio vale per i requisiti. Il test proposto si potrà fare davvero nel collaudo (lezione sulla chiusura).

Specifiche software

Dal requisito alla specifica

Requisito R2

Come volontario voglio iscrivermi a un turno con nome ed email, senza creare un account.

Specifica S2.1 · Iscrizione

  • Input: id del turno, nome (2-60 caratteri), email
  • Controlli: email valida, posti liberi > 0, non già iscritto
  • Output: iscrizione salvata, messaggio, email di conferma
  • Errori: "Turno completo", "Sei già iscritto"
Il requisito parla la lingua dell'utente; la specifica parla la lingua di chi programma e di chi collauda.
La specifica dice che cosa deve fare il software con precisione sufficiente per scriverlo e per provarlo; non dice come è scritto il codice. Ogni specifica è collegata al suo requisito (tracciabilità): se la committente cambia R2, si sa subito quali specifiche e quali test cambiano. Le specifiche vanno nel documento NQ-SPC-001.

Componenti e linguaggi

Tre livelli, un linguaggio per ciascuno

Browser

HTML per la struttura, CSS per l'aspetto, JavaScript per le interazioni.

Server web

PHP riceve le richieste, controlla i dati, prepara le pagine.

Database

MySQL o MariaDB conserva volontari, turni, iscrizioni; si interroga in SQL.

Componenti in più: un'attività pianificata ogni sera invia i promemoria via email (protocollo SMTP); tutto il traffico passa in HTTPS.
La scelta segue la fattibilità tecnica dell'avvio: il server della scuola offre PHP e MySQL e la classe li studia in informatica. Con un altro server la scelta potrebbe essere diversa (per esempio Python o Node.js): l'importante è motivarla nel documento delle specifiche. L'attività pianificata è tipicamente un cron job sul server Linux.

Soluzione: JavaScript sul telefono (insieme a HTML e CSS), HTTPS sulla freccia tra telefono e server, PHP sul server, SQL sulla freccia tra server e database, SMTP verso le email. Distrattori: FTP (un tempo usato per caricare i file sul server, non per gli utenti) e CSV (un formato di file, usato dall'esportazione, non un linguaggio dell'architettura). Far notare che il telefono non parla mai direttamente con il database: tutto passa dal server, che controlla.

Il database

Tre tabelle bastano

volontario

id · nome · email · telefono

iscrizione

volontario_id · turno_id · data_iscrizione

turno

id · attivita · data · ora_inizio · ora_fine · posti

-- posti liberi di un turno
SELECT t.posti - COUNT(i.volontario_id) AS liberi
FROM turno t LEFT JOIN iscrizione i ON i.turno_id = t.id
WHERE t.id = ? GROUP BY t.id, t.posti;
Un volontario fa molti turni e un turno ha molti volontari: relazione molti a molti, risolta dalla tabella iscrizione. La coppia (volontario_id, turno_id) è chiave primaria di iscrizione, quindi la stessa persona non può iscriversi due volte allo stesso turno. Il LEFT JOIN serve per i turni senza iscritti (COUNT dà 0). Il "?" è un parametro: la query si esegue con un prepared statement, che protegge dalla SQL injection. Nessun dato sui minori del doposcuola: è un vincolo del charter.

Metti in ordine

Da una richiesta a una funzione "fatta"

  1. User story con i criteri di accettazione
  2. Schermata nel prototipo, approvata
  3. Specifica con input, controlli, output, errori
  4. Codice e query, nel ramo della squadra
  5. Revisione del codice da parte di un compagno
  6. Prova con i criteri di accettazione
  7. Integrazione nel ramo principale e scheda spostata in "Fatto"
Ordine come scritto. Revisione e prova possono scambiarsi o avvenire in parallelo: accettarlo. Il concetto di "definizione di fatto" è nel deck "lavorare-a-progetti": una funzione non è fatta quando il codice è scritto, ma quando è provata e integrata. Monitoraggio

Ogni settimana: dove siamo rispetto al piano?

Avanzamento

Percentuale fatta di ogni pacchetto, onesta: "quasi finito" non è un numero.

Valore guadagnato

Ore pianificate a oggi (PV) contro ore "guadagnate" dal lavoro fatto (EV).

Azioni

Se un'attività critica è in ritardo: spostare persone, ridurre l'ambito, avvisare.

Indice di avanzamento dei tempiSPI = EV / PV  < 1 → in ritardo
Ripasso dell'Unità 4 (monitoraggio, stato di avanzamento ed Earned Value). Nel progetto NQ i costi sono ore di lavoro, quindi PV ed EV si misurano in ore. Il monitoraggio si fa nella riunione settimanale e finisce nel verbale con le azioni correttive.

Quiz a trabocchetto

Back-end al 70%, manuale al 50%. Quale ritardo preoccupa di più?

  1. Il manuale: è più indietro
  2. Il back-end: è sul percorso critico, ogni giorno perso sposta la fine
  3. Nessuno dei due, lo SPI è vicino a 1
  4. Pesano uguale, perché si misurano in ore

Nel Gantt il back-end (E) è critico: un ritardo lì sposta il rilascio. Il manuale (J) ha 3 settimane di margine: può finire più tardi senza danni, se recupera entro la settimana 9. La percentuale da sola non basta, serve il piano.

Collega monitoraggio e percorso critico (lezione sull'approfondimento). Azioni correttive possibili: spostare un membro della squadra documentazione sul back-end per due settimane (il manuale ha margine); ridurre l'ambito, rimandando l'esportazione CSV a dopo il rilascio, d'accordo con la committente. La C è sbagliata: 0,74 vuol dire che è stato fatto circa tre quarti del lavoro previsto.

Metriche del software

Misurare il prodotto, non solo il progetto

Dimensione

Righe di codice (LOC): utile per confronti, pessima come misura di bravura.

Complessità

Complessità ciclomatica (McCabe, 1976): decisioni + 1 per ogni funzione.

Test

Copertura: quale parte del codice viene eseguita dai test.

Difetti

Bug trovati, risolti, ancora aperti, per gravità.

Prestazioni

Tempo di risposta: R1 chiede meno di 2 s.

Qualità

Il modello ISO/IEC 25010 (aggiornato nel 2023) elenca le caratteristiche da misurare.

Thomas McCabe propose la complessità ciclomatica nel 1976: in pratica, per una funzione senza salti strani, è il numero di decisioni (if, cicli, casi) più uno, e indica il numero minimo di casi di prova per percorrere tutti i cammini indipendenti. La ISO/IEC 25010 descrive il modello di qualità del prodotto software (tra le caratteristiche: idoneità funzionale, efficienza, compatibilità, affidabilità, sicurezza, manutenibilità). Avvertenza: una metrica diventa inutile se diventa un obiettivo da gonfiare (più righe non vuol dire più lavoro utile).

Sfida

Apri il lucchetto: quanto sono complesse?

function iscrivi($v, $t) {
  if (!emailValida($v->email))
    return "Email non valida";
  if ($t->postiLiberi() == 0)
    return "Turno completo";
  if (giaIscritto($v, $t))
    return "Sei già iscritto";
  salva($v, $t);
  return "Iscrizione confermata";
}
function postiLiberi($t) {
  $n = 0;
  foreach ($t->iscrizioni as $i) {
    if ($i->attiva)
      $n++;
  }
  return $t->posti - $n;
}

Prima cifra: complessità ciclomatica di iscrivi. Seconda cifra: quella di postiLiberi.

Aperto! iscrivi: 3 if + 1 = 4. postiLiberi: foreach + if + 1 = 3. Servono almeno 4 casi di prova per iscrivi.
Codice: 43. iscrivi ha tre decisioni (tre if) quindi 4 cammini: email non valida, turno completo, già iscritto, iscrizione confermata; servono almeno 4 casi di prova, uno per messaggio. postiLiberi ha due decisioni (il ciclo e l'if) quindi 3. Codice PHP semplificato a scopo didattico.
