Web service
SOAP in Java

Laboratorio: scriviamo un servizio SOAP vero con Maven e Jakarta XML Web Services, leggiamo il WSDL che genera e costruiamo il client partendo solo dal contratto.

5G TPSIMaven, @WebService, Endpoint, WSDL, wsimport, Fault

Obiettivi: creare un progetto Maven con la dipendenza Jakarta XML Web Services (implementazione Eclipse Metro); pubblicare un servizio con @WebService ed Endpoint.publish; leggere il WSDL generato e collegarlo al codice Java; chiamare il servizio con curl e con un client generato da wsimport; gestire i Fault. Durata: 4 ore (due lezioni da 2 ore). Prerequisiti: lezione 6. Software: JDK 21, IntelliJ IDEA Community (Maven incluso) o VS Code con Extension Pack for Java; la prima volta Maven scarica le librerie da Maven Central (repo.maven.apache.org), circa 15 MB: va permesso dalla rete della scuola, oppure le librerie vanno scaricate prima. Tutto il codice di queste slide è stato provato con JDK 21 e jaxws-rt 4.0.3. Piano B se Maven non può scaricare: il docente esegue il progetto sulla LIM da un hotspot e gli studenti fanno i laboratori con curl (che non richiede librerie) verso il PC del docente, oppure ripetono i laboratori 3 e 4 della lezione 6 con il server senza librerie e ispezionano il WSDL pubblico con il browser o SoapUI.

Il piano del laboratorio

Dal codice al contratto, dal contratto al client

1 · Servizio

Una classe Java con @WebService

2 · Pubblica

Endpoint.publish su localhost:8080/calc

3 · WSDL

Generato da solo: ?wsdl

4 · Client

wsimport legge il WSDL e genera lo stub

Code-first

Scrivo il codice, il framework genera il WSDL. È quello che facciamo per il servizio.

Contract-first

Parto dal WSDL concordato e genero il codice. È quello che facciamo per il client, e che si fa tra aziende.

Il client non vedrà mai il codice del servizio: solo il WSDL, come un'azienda esterna. Nelle integrazioni vere con la PA o con una banca si lavora quasi sempre contract-first: il WSDL è il documento ufficiale concordato (per esempio quello del Sistema di Interscambio per le fatture elettroniche). Due progetti Maven separati: calc-soap (servizio) e calc-client (client).

Mettiti alla prova

Copi un esempio del 2015 con import javax.jws.WebService; e con JDK 21 non compila. Perché?

  1. Bisogna attivare un'opzione del compilatore per SOAP
  2. Il pacchetto è stato rinominato java.soap
  3. JAX-WS è uscito dal JDK con Java 11: ora è una libreria, Jakarta XML Web Services
  4. Java 21 non supporta più i web service SOAP

JAX-WS faceva parte del JDK da Java 6 a Java 10, nei pacchetti javax.xml.ws e javax.jws. Java 11 lo ha rimosso (JEP 320). Oggi si aggiunge con Maven: si chiama Jakarta XML Web Services, i pacchetti sono jakarta.xml.ws e jakarta.jws, l'implementazione di riferimento è Eclipse Metro.

La D è il tranello per chi pensa che "rimosso dal JDK" voglia dire "non più possibile". Con JEP 320 sono usciti dal JDK anche JAXB e CORBA. Il passaggio da javax a jakarta è dovuto al trasferimento di Java EE dalla Oracle alla Eclipse Foundation (2017-2019), che ha dovuto cambiare il nome dei pacchetti. Conseguenza pratica: negli esempi trovati in rete, se c'è javax.jws bisogna sostituirlo con jakarta.jws e usare la dipendenza della versione 3 o 4.

Laboratorio 2: la classe del servizio

package it.scuola.calc;

import jakarta.jws.WebMethod;
import jakarta.jws.WebParam;
import jakarta.jws.WebService;

@WebService(serviceName = "CalcolatriceService")
public class Calcolatrice {
  @WebMethod
  public int somma(@WebParam(name = "a") int a,
                   @WebParam(name = "b") int b) {
    return a + b;
  }
  @WebMethod
  public double dividi(@WebParam(name = "a") double a,
                       @WebParam(name = "b") double b) {
    if (b == 0) throw new IllegalArgumentException("Divisione per zero");
    return a / b;
  }
}
AnnotazioneEffetto
@WebServiceLa classe diventa un servizio; serviceName dà il nome nel WSDL
@WebMethodIl metodo diventa un'operazione
@WebParamNome dell'elemento XML del parametro
Senza @WebParam i parametri si chiamerebbero arg0 e arg1 nel WSDL: funziona, ma il contratto è illeggibile. I metodi pubblici di una classe @WebService sono esposti anche senza @WebMethod; metterlo rende esplicita la scelta (e con @WebMethod(exclude = true) si esclude un metodo). L'eccezione lanciata in dividi diventerà un soap:Fault: lo vedremo con curl. Collegamento con la lezione 2: questa classe è l'implementazione; lo skeleton lo genera Metro a runtime.

Laboratorio 3: pubblica e leggi il WSDL

package it.scuola.calc;

import jakarta.xml.ws.Endpoint;

public class Server {
  public static void main(String[] args) {
    String url = "http://localhost:8080/calc";
    Endpoint.publish(url, new Calcolatrice());
    System.out.println("Servizio attivo: " + url + "?wsdl");
  }
}

Avvialo con il pulsante Run dell'IDE accanto al main.

  1. Crea Server.java ed eseguilo.
  2. Apri nel browser http://localhost:8080/calc?wsdl
  3. Apri anche http://localhost:8080/calc e ?xsd=1.
Controllo: un WSDL con name="CalcolatriceService" e targetNamespace="http://calc.scuola.it/", operazioni somma e dividi. Senza ?wsdl: una pagina "Web Services" con l'elenco degli endpoint.
Endpoint.publish usa il piccolo server HTTP incluso nel JDK (lo stesso HttpServer delle lezioni precedenti): non serve Tomcat. In produzione il servizio si installerebbe in un application server Jakarta EE o in Tomcat con Metro. Il targetNamespace http://calc.scuola.it/ è ricavato dal pacchetto Java it.scuola.calc letto al contrario. Errori tipici: BindException "Address already in use" se la porta 8080 è occupata (chiudere l'altra esecuzione o cambiare porta); ClassNotFoundException su jakarta.xml.ws se Maven non ha caricato le dipendenze. Avviare dall'IDE e non con mvn exec:java: in quel modo, nelle nostre prove, i Fault non vengono serializzati per un problema di caricamento delle classi.

Puzzle

Dal Java al WSDL: chi diventa che cosa?

Pacchetto it.scuola.calc
targetNamespace http://calc.scuola.it/
Classe Calcolatrice
portType Calcolatrice
serviceName
service CalcolatriceService
Metodo somma
operation somma, messaggi somma e sommaResponse
@WebParam(name = "a") int
elemento a di tipo xs:int nello schema
Valore restituito
elemento return
Far verificare ogni coppia nel WSDL aperto nel browser (e nello schema ?xsd=1 per i tipi). L'elemento della risposta si chiama return per default; si può cambiare con @WebResult(name = "risultato"). Domanda: se rinomino il pacchetto Java, che cosa succede ai client già generati? (Cambia il targetNamespace: i vecchi client mandano elementi in un namespace che il server non riconosce, e ricevono un Fault. Per questo nei servizi veri si fissa il namespace con @WebService(targetNamespace = "...").)

Laboratorio 4: chiamalo con curl, come nella lezione 6

curl -i -H "Content-Type: text/xml; charset=utf-8"
     --data-binary @somma.xml http://localhost:8080/calc
  1. Riusa somma.xml della lezione 6 (o riscrivilo): stessa busta, stesso namespace.
  2. Crea dividi.xml: operazione c:dividi con a = 20 e b = 0. Invialo.
  3. Rimanda somma.xml con Content-Type: application/json.
  4. Rinomina l'operazione in c:moltiplica e invia.
  5. Copia le quattro risposte in soap-java-curl-cognome.txt.
Controllo:
1. 200, <return>42</return>
2. 500, Fault S:Server, "Divisione per zero"
3. 415 Unsupported Media Type
4. 500, Fault S:Client, "Cannot find dispatch method for {http://calc.scuola.it/}moltiplica"
Tutte risposte verificate con il codice delle slide. Il file somma.xml della lezione 6 funziona senza modifiche: è la prova che il contratto è lo stesso anche se l'implementazione è cambiata da un server "finto" a un framework vero (accoppiamento debole, lezione 3). Leggere insieme le differenze: il Fault Server viene da un'eccezione Java nel nostro codice; il Fault Client da una richiesta che il framework non sa smistare; il 415 è HTTP che rifiuta il tipo di contenuto prima ancora di guardare la busta (lezione 5). Nel server, la console mostra lo stack trace dell'eccezione: il client invece riceve solo il messaggio, ed è giusto così per la sicurezza.

Quiz a trabocchetto

Mandi al servizio vero la busta senza l'elemento <a>. Che cosa risponde?

  1. 200 con <return>22</return>
  2. Un Fault Client: "manca il parametro a"
  3. 400 Bad Request
  4. Il server va in crash e si ferma

Di default Metro non valida i messaggi rispetto allo schema: il parametro mancante diventa il valore predefinito di un int, cioè 0, e 0 + 22 = 22. Il server finto della lezione 6 rispondeva con un Fault; quello "vero" no. Per pretendere un messaggio corretto bisogna attivare la validazione.

Risultato verificato. Quasi tutti scelgono B, convinti che un framework serio controlli tutto. Lezione importante: un contratto c'è, ma non sempre viene fatto rispettare. Soluzione: l'annotazione @SchemaValidation di Metro (pacchetto com.sun.xml.ws.developer) sulla classe del servizio: con lei la stessa richiesta riceve un Fault Client con il messaggio del validatore ("Invalid content was found starting with element 'b'. One of '{a}' is expected."). Anche questo è verificato. È un'estensione specifica di Metro, non dello standard. In alternativa si controllano i valori nel codice e si lancia un'eccezione.

Laboratorio 5: il client nasce dal WSDL

<!-- pom.xml di calc-client: stessa dipendenza jaxws-rt, più -->
<build><plugins>
  <plugin>
    <groupId>com.sun.xml.ws</groupId>
    <artifactId>jaxws-maven-plugin</artifactId>
    <version>4.0.3</version>
    <executions><execution>
      <goals><goal>wsimport</goal></goals>
      <configuration>
        <wsdlUrls>
          <wsdlUrl>http://localhost:8080/calc?wsdl</wsdlUrl>
        </wsdlUrls>
        <packageName>it.scuola.client.gen</packageName>
      </configuration>
    </execution></executions>
  </plugin>
</plugins></build>
  1. Lascia acceso il servizio. Crea un secondo progetto Maven calc-client.
  2. Nel pom: la stessa dipendenza jaxws-rt e, dopo </dependencies>, questo blocco build.
  3. Esegui mvn compile (in IntelliJ: finestra Maven, Lifecycle, compile).
Controllo: nel log "parsing WSDL… Generating code…" e in target/generated-sources/wsimport le classi Calcolatrice, CalcolatriceService, Somma, SommaResponse, ObjectFactory…
wsimport legge il WSDL e lo schema e genera: l'interfaccia Calcolatrice (la SEI, Service Endpoint Interface, con i metodi somma e dividi), la classe CalcolatriceService (la "fabbrica" del proxy, con l'indirizzo letto dal WSDL), le classi JAXB per i messaggi (Somma, SommaResponse, Dividi, DividiResponse) e ObjectFactory. Sono lo stub della lezione 2, generato dal contratto. Se compare "Connection refused" il servizio non è acceso. In alternativa si può salvare il WSDL in un file e usare wsdlFiles invece di wsdlUrls: utile quando il servizio non è raggiungibile mentre si compila.

Laboratorio 6: il client chiama, e gestisce il Fault

package it.scuola.client;

import it.scuola.client.gen.Calcolatrice;
import it.scuola.client.gen.CalcolatriceService;

public class Client {
  public static void main(String[] args) {
    Calcolatrice calc =
        new CalcolatriceService().getCalcolatricePort();
    System.out.println("20 + 22 = " + calc.somma(20, 22));
    try {
      System.out.println(calc.dividi(1, 0));
    } catch (jakarta.xml.ws.soap.SOAPFaultException e) {
      System.out.println("Fault dal server: " + e.getMessage());
    }
  }
}
  1. Crea Client.java nel pacchetto it.scuola.client ed eseguilo.
  2. Spegni il servizio e rilancia il client: che cosa succede?
Controllo: 20 + 22 = 42, poi Fault dal server: Client received SOAP Fault from server: Divisione per zero… A servizio spento: un'eccezione di connessione.
Output verificato. Nel codice del client non c'è traccia di XML, HTTP o socket: è esattamente l'RPC della lezione 2, con lo stub generato dal WSDL. Il nome getCalcolatricePort viene dal nome della port nel WSDL (CalcolatricePort). Il Fault arriva come SOAPFaultException, che è una RuntimeException: il compilatore non obbliga a gestirla (diverso da RMI, dove RemoteException è controllata). Discussione: è meglio così? A servizio spento, la creazione di CalcolatriceService fallisce già perché il proxy rilegge il WSDL dall'URL: si può evitare salvando il WSDL in locale. Estensione: misurare con System.nanoTime() quanto dura una chiamata somma in remoto rispetto a una somma locale.

Sfida a squadre: il servizio Registro

  1. Squadre da 3: uno scrive il servizio, uno il client, uno prepara le buste di test con curl.
  2. Aggiungi al progetto un servizio Registro con aggiungiVoto(studente, voto) e media(studente), con i voti in una Map.
  3. Voto fuori da 1-10 o studente sconosciuto: lancia un'eccezione con un messaggio chiaro.
  4. Pubblicalo su /registro nello stesso main, rigenera il client con wsimport e provalo.
  5. Consegna registro-soap-squadra.zip (i due progetti senza la cartella target, più le buste di test).
Controllo: dopo aggiungiVoto("Ada", 8) e aggiungiVoto("Ada", 9), media("Ada") vale 8.5; aggiungiVoto("Ada", 11) restituisce un Fault.
Soluzione di riferimento: classe @WebService(serviceName = "RegistroService") public class Registro { private final Map<String, List<Integer>> voti = new ConcurrentHashMap<>(); @WebMethod public void aggiungiVoto(@WebParam(name="studente") String s, @WebParam(name="voto") int v) { if (v < 1 || v > 10) throw new IllegalArgumentException("Voto non valido: " + v); voti.computeIfAbsent(s, k -> new CopyOnWriteArrayList<>()).add(v); } @WebMethod public double media(@WebParam(name="studente") String s) { List<Integer> l = voti.get(s); if (l == null) throw new IllegalArgumentException("Studente sconosciuto: " + s); return l.stream().mapToInt(Integer::intValue).average().orElse(0); } }. Nel Server: una seconda riga Endpoint.publish("http://localhost:8080/registro", new Registro()). Nel pom del client: un secondo wsdlUrl. Il servizio è un'unica istanza condivisa da tutte le richieste, eseguite su thread diversi: per questo la Map è concorrente (collegamento con l'Unità 3). Valutare anche la qualità delle buste di test: chi prova i casi d'errore merita di più. Attenzione, verificato nelle nostre prove: se due servizi nello stesso pacchetto Java hanno un'operazione con lo stesso nome (per esempio media), Metro genera due classi wrapper con lo stesso nome e la pubblicazione fallisce con "do not have a property of the name…"; si risolve mettendo il servizio in un pacchetto diverso.

Oggi

Un vecchio servizio SOAP, un nuovo utente: l'AI

Oggi

Molte aziende vogliono che i loro assistenti AI usino i sistemi interni, spesso servizi SOAP di anni fa. Una soluzione frequente è scrivere un piccolo server MCP che espone strumenti semplici, per esempio "media dei voti di uno studente", e dietro chiama il servizio SOAP con un client generato da wsimport. Il modello vede JSON-RPC; il servizio continua a vedere buste XML.

Il ponte, in tre livelli

  1. Agente AI → MCP (JSON-RPC)
  2. Server MCP in Java → stub wsimport
  3. Stub → servizio SOAP (XML su HTTP)
È il pattern "adapter" applicato all'architettura: nessuna modifica al servizio esistente, un nuovo strato che traduce. Temi da discutere: sicurezza (quali operazioni lasciare all'agente? un "aggiungiVoto" va protetto molto più di un "media"), idempotenza (lezione 2: se l'agente riprova, non deve inserire due voti), log e controllo umano. Esistono SDK ufficiali per scrivere server MCP in Java; non è richiesto in questo corso.
