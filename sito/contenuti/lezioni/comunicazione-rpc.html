L'osservazione

Tutti i programmatori sanno usare una chiamata di procedura. Allora facciamo sembrare una chiamata anche la comunicazione in rete.

La difficoltà

Il resto dell'articolo, decine di pagine, spiega perché realizzarla bene non è semplice per niente: guasti, nomi, prestazioni.

Originale: "The idea of remote procedure calls (hereinafter called RPC) is quite simple." È l'inizio della sezione introduttiva dell'articolo pubblicato su ACM Transactions on Computer Systems nel febbraio 1984. Traduzione nostra. L'ironia è voluta dagli autori: l'idea è semplice, l'implementazione no. Lo stesso decennio vede la Sun RPC (ONC RPC), usata ancora oggi dal file system di rete NFS. Domanda: quali problemi esistono in rete e non in una chiamata locale? Far emergere: la rete può perdere messaggi, il server può essere spento, i dati vanno convertiti, il tempo di risposta è mille o un milione di volte più alto.

Come funziona

Il trucco: due sostituti, uno per parte

Client

chiama somma(2, 3) come un metodo qualunque

Stub client

impacchetta nome e parametri in byte (marshalling)

Rete

il messaggio viaggia su TCP o UDP

Skeleton

spacchetta (unmarshalling) e chiama il metodo vero

Server

esegue somma e restituisce 5

La risposta fa il percorso al contrario: il client non vede né socket né byte.

All'esame: questo schema si disegna come diagramma di sequenza, con una colonna per client, stub, rete, skeleton e server.
Lo stub client (detto anche proxy) ha la stessa interfaccia del servizio remoto: per il client è indistinguibile dall'oggetto vero. Lo skeleton (o stub server) riceve i messaggi, li decodifica e chiama l'implementazione. In molti sistemi stub e skeleton sono generati automaticamente da una descrizione dell'interfaccia scritta in un IDL (Interface Definition Language): file .x per Sun RPC, interfacce Java per RMI, file .proto per gRPC, WSDL per SOAP. Far disegnare alla lavagna il diagramma di sequenza: è un esercizio d'esame classico.

Marshalling

Trasformare i parametri in byte, e ritorno

  • Client e server devono essere d'accordo sul formato: quanti byte per un int, come si scrive una stringa.
  • Ordine dei byte: le CPU Intel e ARM lavorano in little-endian, in rete si usa per tradizione il big-endian.
  • I puntatori e i riferimenti non hanno senso su un'altra macchina: si passa una copia del dato.
  • Formati binari (compatti, veloci) o testuali (XML, JSON: leggibili, più grandi).

Passaggio per copia

In locale, se il metodo modifica l'oggetto ricevuto, il chiamante vede la modifica.

In remoto il server lavora su una copia: il chiamante non vede nulla, a meno che il valore non torni nella risposta.

Una delle differenze che la "trasparenza" non può nascondere.

Il termine marshalling viene dall'idea di "schierare in ordine" i dati per il trasporto. Sinonimi frequenti: serializzazione, codifica. Big-endian è detto anche network byte order (RFC 1700); Java scrive sempre in big-endian con DataOutputStream, qualunque sia la CPU. Domanda: se il client Java invia un int a un server C su un PC Intel che lo legge così com'è, che cosa succede? (Legge il numero con i byte invertiti: 2 diventa 33 554 432.) Il prossimo laboratorio mostra i byte veri.

Al computer · 15 minuti

Guarda i byte di una chiamata

import java.io.*;

public class Marshal {
  public static void main(String[] a) throws IOException {
    var buf = new ByteArrayOutputStream();
    var out = new DataOutputStream(buf);
    out.writeUTF("somma");   // nome del metodo
    out.writeInt(2);         // primo parametro
    out.writeInt(300);       // secondo parametro
    for (byte b : buf.toByteArray())
      System.out.printf("%02X ", b);
    System.out.println("\n" + buf.size() + " byte");
    var in = new DataInputStream(
        new ByteArrayInputStream(buf.toByteArray()));
    System.out.println(in.readUTF() + "(" + in.readInt()
        + ", " + in.readInt() + ")");
  }
}
  1. Scrivi Marshal.java ed eseguilo con java Marshal.java.
  2. Trova nei byte la lunghezza della stringa, le lettere e i due int.
  3. Cambia 300 in -1: che byte ottieni?
Controllo: 00 05 73 6F 6D 6D 61 00 00 00 02 00 00 01 2C, 15 byte, poi somma(2, 300). Con -1 ottieni FF FF FF FF.
Lettura dei byte: 00 05 è la lunghezza della stringa (writeUTF scrive prima due byte di lunghezza), 73 6F 6D 6D 61 sono s o m m a in ASCII, 00 00 00 02 è il 2 su 4 byte in big-endian, 00 00 01 2C è 300 (0x12C = 256 + 44). -1 in complemento a due è FF FF FF FF. Il lato "server" è simulato dalla DataInputStream: deve leggere nello stesso ordine in cui il client ha scritto, altrimenti ottiene numeri senza senso. Esperimento: invertire le due readInt con readUTF e osservare l'eccezione o i valori sbagliati. Questo è esattamente il lavoro che stub e skeleton fanno per noi.

Puzzle

Metti in ordine una chiamata remota

  1. Il client chiama il metodo sullo stub locale
  2. Lo stub fa il marshalling di nome e parametri
  3. Il messaggio viaggia in rete fino al server
  4. Lo skeleton fa l'unmarshalling e chiama il metodo vero
  5. Il server esegue e restituisce il risultato allo skeleton
  6. La risposta torna in rete e lo stub la decodifica
  7. Il client riceve il valore di ritorno e riprende
Errore frequente: mettere l'esecuzione prima dell'unmarshalling, o dimenticare che anche la risposta richiede marshalling. Far notare che il client, in una chiamata sincrona, resta bloccato dal passo 1 al passo 7: per tutto quel tempo non fa altro. Domanda: in quale passo può guastarsi qualcosa? (In tutti: è il motivo della prossima slide.)

Quiz a trabocchetto

Il client chiama versa(conto, 100) e dopo 5 secondi scatta il timeout. Che cosa sa?

  1. Che il server non ha eseguito il versamento
  2. Che il server ha eseguito, ma la risposta si è persa
  3. Che la rete gli manderà un'eccezione con la causa precisa
  4. Niente di certo: richiesta persa, server lento o risposta persa

Da fuori i tre casi sono identici: il client non riceve niente. Il server potrebbe aver versato i 100 euro oppure no. Per questo una chiamata remota non sarà mai uguale a una locale, e bisogna progettare cosa fare quando si riprova.

È il cuore della lezione. Molti scelgono A (pensano che il timeout significhi "non fatto") o C (pensano che l'eccezione dica la causa). In realtà il client sa solo che non ha ricevuto risposta in tempo. Collegamento con il saggio "A Note on Distributed Computing" (Waldo, Wyant, Wollrath, Kendall, Sun Microsystems, 1994): latenza, accesso alla memoria, guasto parziale e concorrenza rendono impossibile trattare in modo identico oggetti locali e remoti. Ann Wollrath è anche tra i principali autori di Java RMI.

Semantiche di invocazione

Se riprovo, quante volte viene eseguito?

SemanticaCome si ottieneRischio
Almeno una voltaIl client ritrasmette finché non riceve rispostaEsecuzioni doppie
Al più una voltaIl server ricorda gli ID già visti e scarta i duplicatiPuò non essere eseguita mai
Esattamente una voltaRitrasmissione + ID + memoria persistente sul serverCostosa, difficile da garantire

Idempotente

Eseguirla due volte dà lo stesso effetto di una: leggiSaldo(), impostaEmail(x). Si può riprovare senza paura.

Non idempotente

versa(100) eseguita due volte versa 200. Si protegge con un ID univoco della richiesta.

Java RMI offre la semantica "al più una volta": se c'è un errore di rete il client riceve una RemoteException e decide lui. Esempio reale di ID di richiesta: molte API di pagamento, come Stripe, accettano un header Idempotency-Key; se la stessa chiave arriva due volte, il server restituisce il risultato della prima esecuzione invece di addebitare di nuovo. Lo ritroveremo con HTTP: GET, PUT e DELETE sono idempotenti per specifica, POST no.

Mettiti alla prova

La risposta si è persa. Quale chiamata puoi ripetere senza danni?

  1. creaOrdine(carrello)
  2. impostaIndirizzo(utente, "Via Roma 1")
  3. aggiungiPunti(utente, 10)
  4. inviaNotifica(utente, "Spedito")

Impostare l'indirizzo a "Via Roma 1" due volte lascia lo stesso stato: è idempotente. Le altre, ripetute, creano due ordini, aggiungono 20 punti o mandano due notifiche.

La D è il tranello: "tanto è solo una notifica". Due notifiche uguali sono un fastidio, ma il principio vale: l'effetto non è lo stesso. Chiedere come rendere idempotente aggiungiPunti: trasformarla in aggiungiPunti(utente, 10, idOperazione) e far ricordare al server gli ID già applicati, oppure in impostaPunti(utente, totale) se il client conosce il totale.

Sincrona o asincrona

Aspettare la risposta, oppure no

Sincrona

Il client si blocca finché arriva la risposta. Semplice da scrivere, ma un server lento blocca anche il client.

Java RMI, una chiamata HTTP classica

Asincrona

Il client riceve subito un future o registra una callback e continua a lavorare.

sendAsync di HttpClient, gli stub asincroni di gRPC

Senza risposta

Il client invia e non aspetta nulla (one-way). Utile per log e notifiche.

Non sa mai se è arrivata

var futuro = client.sendAsync(req, BodyHandlers.ofString());   // non si blocca
// ... intanto il programma fa altro ...
futuro.thenAccept(r -> System.out.println(r.body()));            // callback
Le app con interfaccia grafica, Android compreso (Unità 4), non possono fare chiamate di rete sincrone sul thread principale: l'interfaccia si bloccherebbe. Su Android una chiamata di rete sul thread principale provoca NetworkOnMainThreadException. sendAsync restituisce un CompletableFuture<HttpResponse<String>>. Domanda: in un'app di chat, l'invio di un messaggio è meglio sincrono o asincrono? (Asincrono, con un indicatore "inviato" che compare quando arriva la conferma.)

Java RMI

RPC a oggetti, già dentro il JDK

  • L'interfaccia remota estende java.rmi.Remote; ogni metodo dichiara throws RemoteException.
  • Il server esporta l'oggetto: Java crea lo stub e apre una porta.
  • Il registro RMI (porta 1099) associa un nome allo stub: è il servizio di binding.
  • Il client fa lookup("calc"), riceve lo stub e chiama i metodi.
  • Parametri e risultati devono essere Serializable o a loro volta remoti.

Pregi e limiti

+ nessuna libreria esterna, tipi Java veri, eccezioni.

− solo Java con Java: niente interoperabilità con altri linguaggi.

− passa male i firewall: porte dinamiche, protocollo proprietario.

Per questo sul Web hanno vinto i web service.

RMI è nel JDK dalla versione 1.1 (1997) ed è ancora presente in Java 21 (modulo java.rmi); è stata rimossa nel JDK 17 solo la parte di "attivazione". La RemoteException obbligatoria è una scelta voluta: costringe il programmatore a ricordare che la chiamata è remota e può fallire. È la lezione di Waldo e colleghi messa nel linguaggio. Nei due laboratori seguenti si scrive un servizio RMI completo.

Al computer · 20 minuti

Un servizio RMI: interfaccia e server

// ServerRmi.java
import java.rmi.registry.*;
import java.rmi.server.UnicastRemoteObject;
public class ServerRmi implements Calcolatrice {
  static Registry registro;      // da tenere vivo
  public int somma(int a, int b) {
    System.out.println("Chiamata remota: somma(" + a + ", " + b + ")");
    return a + b;
  }
  public static void main(String[] args) throws Exception {
    Calcolatrice stub = (Calcolatrice)
        UnicastRemoteObject.exportObject(new ServerRmi(), 0);
    registro = LocateRegistry.createRegistry(1099);
    registro.rebind("calc", stub);
    System.out.println("Server RMI pronto sulla porta 1099");
  }
}
// Calcolatrice.java
import java.rmi.*;
public interface Calcolatrice
    extends Remote {
  int somma(int a, int b)
      throws RemoteException;
}
  1. Cartella rmi con i due file, poi javac *.java
  2. Avvia java ServerRmi e lascia aperta la finestra.
Controllo: compare Server RMI pronto e il programma resta in attesa di chiamate.
exportObject con porta 0 lascia scegliere al sistema una porta libera per l'oggetto: il registro sulla 1099 serve solo a trovarlo. Il campo statico registro evita che il registro venga eliminato dal garbage collector. Se Windows chiede di consentire l'accesso alla rete a Java, per una prova in locale basta "Reti private"; in coppia su due PC serve che il firewall della scuola lasci passare le porte (spesso non è così: in quel caso restare su localhost). Errore tipico: "port already in use" se un compagno o un'esecuzione precedente occupa la 1099; chiudere l'altra finestra.

Al computer · 15 minuti

Il client RMI, e che cosa succede quando il server cade

// ClientRmi.java
import java.rmi.registry.*;
public class ClientRmi {
  public static void main(String[] args) throws Exception {
    String host = args.length > 0 ? args[0] : "localhost";
    Registry registro = LocateRegistry.getRegistry(host, 1099);
    Calcolatrice calc = (Calcolatrice) registro.lookup("calc");
    System.out.println("Ho in mano: " + calc.getClass().getName());
    System.out.println("2 + 3 = " + calc.somma(2, 3));
  }
}
  1. In un secondo terminale: javac ClientRmi.java e java ClientRmi
  2. Guarda anche la finestra del server.
  3. Ferma il server con Ctrl+C e rilancia il client.
Controllo: il client stampa una classe come jdk.proxy1.$Proxy0 (lo stub!) e 2 + 3 = 5. A server spento: ConnectException.
Il nome della classe stampato dimostra che il client non ha in mano l'oggetto ServerRmi, ma un proxy dinamico generato dal JDK: lo stub. Il nome esatto può variare (jdk.proxy1.$Proxy0, jdk.proxy2.$Proxy1). La ConnectException a server spento è la "trasparenza che si rompe": la chiamata sembra locale finché la rete funziona. Variante in coppia, se la rete lo permette: il server su un PC, il client su un altro con "java ClientRmi 192.168.x.y". Estensione: aggiungere all'interfaccia un metodo dividi(double, double) che lancia un'eccezione se b è zero, e vedere come arriva al client.

gRPC

L'RPC moderno: un contratto, tanti linguaggi

// calcolatrice.proto
syntax = "proto3";
service Calcolatrice {
  rpc Somma (Operandi) returns (Risultato);
}
message Operandi  { int32 a = 1; int32 b = 2; }
message Risultato { int32 valore = 1; }
  • Creato da Google, open source dal 2015.
  • Il file .proto è l'IDL: da qui si generano stub per Java, Python, Go, C#, Kotlin…
  • Dati in Protocol Buffers, binario e compatto: Operandi{a=2, b=300} diventa 08 02 10 AC 02, 5 byte.
  • Viaggia su HTTP/2: più chiamate sulla stessa connessione, streaming nei due sensi.

Oggi

gRPC è ovunque nell'infrastruttura del cloud: Kubernetes lo usa per parlare con i runtime dei container, il database etcd che regge Kubernetes espone un'API gRPC. Tra microservizi interni è spesso preferito a JSON perché è più veloce da codificare e più piccolo.

Codifica Protocol Buffers dei 5 byte: 08 = campo 1 di tipo varint, 02 = valore 2; 10 = campo 2 varint; AC 02 = 300 in varint (7 bit per byte, il bit alto dice "continua": 300 = 0101100 + 10, quindi 0xAC poi 0x02). Con DataOutputStream gli stessi due int occupavano 8 byte. I numeri dopo l'uguale nel .proto non sono valori ma numeri di campo: identificano il campo nei byte, per questo non vanno mai cambiati quando si aggiorna il servizio. Curiosità: secondo il progetto la "g" cambia significato a ogni versione; nella 1.0 stava per "gRPC" stesso, un acronimo ricorsivo. In un browser gRPC non si usa direttamente: serve gRPC-Web o un gateway, uno dei motivi per cui le API pubbliche restano spesso REST con JSON.

Oggi

Model Context Protocol

Presentato da Anthropic nel 2024 e adottato da molti strumenti di AI, MCP collega un modello linguistico a strumenti e dati esterni. I messaggi sono JSON-RPC 2.0: con tools/list l'app scopre gli strumenti, con tools/call li chiama. Il modello sceglie lo strumento; la chiamata vera la fa il programma, come uno stub.

Precisione importante: il modello linguistico non apre connessioni. Produce una richiesta strutturata ("voglio usare lo strumento meteo con citta=Milano"); è l'applicazione client che invia il messaggio JSON-RPC al server MCP e poi passa il risultato al modello. I trasporti previsti dalla specifica sono stdio (processo locale) e HTTP. Tutto ciò che abbiamo detto su RPC vale anche qui: timeout, errori, idempotenza (uno strumento che invia email non va ripetuto alla leggera), sicurezza (chi autorizza la chiamata?). Gli studenti hanno già visto agenti AI nella lezione claude-code. Il prossimo laboratorio costruisce un mini server JSON-RPC.

Al computer · 25 minuti

Un mini server JSON-RPC, provato con curl

var srv = HttpServer.create(new InetSocketAddress(8090), 0);
srv.createContext("/rpc", ex -> {
  String q = new String(ex.getRequestBody().readAllBytes());
  Matcher p = Pattern.compile("\\[(-?\\d+),\\s*(-?\\d+)\\]").matcher(q);
  Matcher id = Pattern.compile("\"id\":\\s*(\\d+)").matcher(q);
  String n = id.find() ? id.group(1) : "null";
  String r = q.contains("\"somma\"") && p.find()
    ? "\"result\":" + (Integer.parseInt(p.group(1)) + Integer.parseInt(p.group(2)))
    : "\"error\":{\"code\":-32601,\"message\":\"Method not found\"}";
  byte[] out = ("{\"jsonrpc\":\"2.0\"," + r + ",\"id\":" + n + "}").getBytes();
  ex.getResponseHeaders().set("Content-Type", "application/json");
  ex.sendResponseHeaders(200, out.length);
  ex.getResponseBody().write(out);
  ex.close();
});
srv.start();
  1. JsonRpc.java: codice nel main; import di HttpServer, InetSocketAddress e java.util.regex.
  2. richiesta.json: chiama somma con params [2, 40] e id 1.
  3. curl -d @richiesta.json http://localhost:8090/rpc
  4. Prova un metodo che non esiste.
Controllo: {"jsonrpc":"2.0","result":42,"id":1}. Con un metodo sconosciuto: "error":{"code":-32601,…}, il codice che JSON-RPC 2.0 riserva a "Method not found".
Contenuto di richiesta.json: {"jsonrpc": "2.0", "method": "somma", "params": [2, 40], "id": 1}. Mettere la richiesta in un file evita i problemi con le virgolette nel Prompt dei comandi; in PowerShell usare curl.exe. Il server è volutamente rudimentale: usa espressioni regolari invece di un vero parser JSON (in un progetto vero si userebbe una libreria come Jackson o Gson). Far notare che anche con un errore il codice HTTP è 200: in JSON-RPC l'errore sta nel corpo del messaggio, non nel protocollo di trasporto; con REST (lezioni successive) sarà il contrario. Estensione: aggiungere il metodo "moltiplica"; rispondere con il codice -32602 "Invalid params" se i parametri mancano.
