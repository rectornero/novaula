Una tesi di dottorato del 2000

REST nasce per descrivere il Web

REST non è un protocollo, né un formato, né una libreria: è uno stile architetturale, un insieme di vincoli. HTTP è il protocollo che lo realizza meglio.
La tesi si intitola "Architectural Styles and the Design of Network-based Software Architectures"; REST è descritto nel capitolo 5, la frase sul nome è nel capitolo 6.1. Traduzione nostra dall'inglese, con un taglio segnalato dalle parentesi. Fielding non inventò REST dal nulla: mentre lavorava agli standard del Web (HTTP/1.0, HTTP/1.1, la sintassi degli URI, il server Apache) cercava di spiegare perché il Web scalava così bene, e ne ricavò i vincoli. Domanda: perché "stato" e "trasferimento"? Ogni pagina che ricevi è una rappresentazione dello stato dell'applicazione; cliccando un link passi allo stato successivo.

Messaggio chiave: SOAP non è "vecchio e sbagliato". È ancora usato dove servono contratti rigidi e standard WS-* (sicurezza, transazioni), per esempio in molti servizi della Pubblica Amministrazione e del settore bancario. REST ha vinto sul Web pubblico perché è più leggero, usa ciò che HTTP già offre (cache, codici, proxy) e si prova con un browser. Domanda: con SOAP, se tutte le richieste sono POST verso lo stesso URL, può una cache HTTP aiutare? (No, perché POST non è cacheabile per definizione e l'URL non identifica la risorsa.)

I vincoli di Fielding

Sei vincoli, uno sopra l'altro

VincoloChe cosa chiede
Client-serverInterfaccia separata dai dati: client e server evolvono in modo indipendente
StatelessOgni richiesta contiene tutto ciò che serve: il server non ricorda la "conversazione"
CacheOgni risposta dice se e per quanto si può riusare
Interfaccia uniformeRisorse con URI, rappresentazioni, messaggi autodescrittivi, link (HATEOAS)
Sistema a livelliIl client non sa se parla con il server o con un proxy, una CDN, un gateway
Codice su richiestaFacoltativo: il server può inviare codice da eseguire, come JavaScript
Nella tesi i vincoli sono introdotti uno alla volta, partendo dallo stile "nullo": client-server, stateless, cache, interfaccia uniforme, sistema a livelli, codice su richiesta (l'unico facoltativo). L'interfaccia uniforme ha quattro sotto-vincoli: identificazione delle risorse, manipolazione tramite rappresentazioni, messaggi autodescrittivi, ipermedia come motore dello stato dell'applicazione (HATEOAS). Domanda: se un'API usa una sessione lato server (il server ricorda il carrello per un cookie di sessione), quale vincolo viola? (Stateless. Molte API reali lo violano ed è un compromesso: lo stato si sposta in un database o in un token.)

Puzzle

Abbina ogni vincolo al beneficio che porta

Stateless
Un bilanciatore può mandare ogni richiesta a un server diverso
Cache
Meno richieste al server e risposte più rapide
Sistema a livelli
Si può mettere una CDN davanti al server senza cambiare il client
Interfaccia uniforme
Un client che conosce HTTP sa già come usare qualsiasi risorsa
Client-server
L'app mobile e il sito usano lo stesso back-end
Lavoro a coppie, 3 minuti. Il collegamento più utile per l'esame è stateless e scalabilità orizzontale: se nessun server ricorda la conversazione, posso aggiungere server dietro a un load balancer senza "sessioni appiccicose". Collegamento con la lezione 3 sulle architetture a servizi: i microservizi usano quasi sempre API REST interne, e l'API gateway è un esempio di sistema a livelli.

Risorse e URI

Gli URI sono nomi, i metodi sono verbi

Così no

  • GET /getLibro?id=3
  • POST /cancellaLibro
  • GET /libri/3/elimina
  • POST /api?azione=nuovoPrestito

Così sì

  • GET /libri/3
  • DELETE /libri/3
  • GET /libri?autore=Calvino
  • POST /libri/3/prestiti
  • Nomi al plurale per le collezioni, un identificatore per il singolo elemento.
  • Gerarchia nel percorso, filtri e ordinamenti nella query string.
Una risorsa è qualsiasi cosa abbia un nome: un libro, l'elenco dei libri, i prestiti di un libro, perfino "il meteo di Roma adesso". L'URI la identifica; la rappresentazione (JSON, XML) è ciò che viaggia. Il caso GET /libri/3/elimina è il più pericoloso: un crawler o un'anteprima dei link segue i GET e cancellerebbe i libri. Sono convenzioni diffuse, non regole della tesi: Fielding parla di identificazione delle risorse, non di plurali. Altre convenzioni: minuscole, trattini invece di underscore, versione nel percorso (/v1/) o in un header.

Dalla lezione 5, sui metodi di BiblioAPI

Sicuro, idempotente: due parole da sapere

Metodo e URIChe cosa faSicuroIdempotente
GET /libriLegge l'elencosìsì
GET /libri/3Legge un librosìsì
POST /libriCrea un libro, il server sceglie l'idnono
PUT /libri/3Sostituisce tutto il libro 3nosì
PATCH /libri/3Modifica solo alcuni campinonon garantito
DELETE /libri/3Elimina il libro 3nosì

Sicuro: non cambia lo stato del server. Idempotente: ripetere la stessa richiesta lascia il server come dopo la prima volta.

Le definizioni sono quelle della RFC 9110 (HTTP Semantics, 2022), sezioni 9.2.1 e 9.2.2. Perché conta l'idempotenza: se la rete cade e non so se la richiesta è arrivata, posso ripeterla senza danni solo se è idempotente. Un POST ripetuto crea due libri, o due pagamenti: per questo le API di pagamento accettano una "idempotency key" in un header. PATCH può essere idempotente o no a seconda del formato della modifica (per esempio "anno = 1957" sì, "incrementa le copie di 1" no). Domanda: GET che incrementa un contatore di visite è ancora "sicuro"? (Per la RFC sì, se l'effetto non è richiesto dal client e non è una sua responsabilità.)

Quiz a trabocchetto

Per un timeout il client ripete tre volte PUT /libri/3 e tre volte POST /libri. Quanti libri in più ci sono?

  1. Nessuno: il server riconosce da solo le richieste doppie
  2. Sei: ogni richiesta riuscita scrive qualcosa
  3. Uno: i POST uguali vengono uniti
  4. Tre: i PUT sostituiscono sempre lo stesso libro 3, ogni POST ne crea uno nuovo

PUT è idempotente: indica la risorsa (/libri/3) e il suo stato completo, quindi ripeterlo non cambia il risultato. POST chiede al server di creare una risorsa nuova scegliendo lui l'URI: tre POST, tre libri.

Riprende la definizione di idempotenza della lezione 5 dal punto di vista di chi progetta. La A è il tranello: HTTP non deduplica nulla da solo. Le API serie risolvono il problema dei POST ripetuti con una chiave di idempotenza: il client genera un identificativo unico e lo manda in un header (per esempio Idempotency-Key); se il server lo ha già visto, restituisce la risposta precedente senza creare un secondo libro. È il modo in cui le API di pagamento evitano doppi addebiti. Collegamento con il quiz sul timeout della lezione 2 (RPC): da fuori non si sa se la richiesta è stata eseguita.

Una buona API risponde 201 con l'header Location: /libri/4 quando crea, 204 quando cancella, e mette nel corpo degli errori un JSON che spiega il motivo.
Ripasso dalla lezione 5 su HTTP, ma visto da chi progetta. Errori tipici di progetto: rispondere 200 con {"errore": "..."} nel corpo (il client e i proxy credono che sia andato tutto bene); usare 500 per un input sbagliato (la colpa è del client: 400 o 422); confondere 401 (chi sei? manca o è scaduta l'autenticazione) e 403 (so chi sei ma non puoi). 409 Conflict è perfetto per "il libro è già in prestito". 405 Method Not Allowed quando il metodo non è previsto sulla risorsa, con l'header Allow.

Mettiti alla prova

Quale di queste scelte viola il vincolo stateless?

  1. Ogni richiesta porta il token nell'header Authorization
  2. Il server ricorda la pagina di ogni utente: GET /libri/avanti dà la successiva
  3. L'elenco si sfoglia con GET /libri?pagina=3
  4. Le risposte contengono Cache-Control: max-age=60

Nella B il significato della richiesta dipende da ciò che il server ricorda delle richieste precedenti: se la richiesta arriva a un altro server dietro il bilanciatore, la "pagina successiva" non esiste. Nella C tutto ciò che serve è nella richiesta stessa.

La A è il tranello: "il server deve controllare il token" sembra stato, ma il token viaggia in ogni richiesta e il server può verificarlo senza ricordare nulla (per esempio un JWT firmato). La D realizza un altro vincolo, la cache, ed è perfettamente compatibile. Collegamento con la lezione 1: stateless significa che posso aggiungere server dietro un bilanciatore senza sessioni "appiccicose". Lo stato dell'utente non sparisce: si sposta nel client o in un database condiviso.

Controllo: con l'URL giusto lo stato è 200, il tipo application/json, e il JSON ha un oggetto current con temperature_2m e un oggetto current_units con °C. Senza latitudine il server risponde 400 con un messaggio d'errore.
Open-Meteo è un servizio meteo gratuito per uso non commerciale e non richiede chiave né account; controllare prima della lezione che sia raggiungibile dalla rete della scuola (dominio api.open-meteo.com). Rappresentazioni

Una risorsa, più rappresentazioni

GET /api/libri/2 HTTP/1.1
Accept: application/json
Authorization: Bearer eyJhbGciOi…

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60

{ "id": 2,
  "titolo": "Il barone rampante",
  "autore": "Italo Calvino",
  "anno": 1957 }
  • Il client chiede un formato con Accept, il server dice quale manda con Content-Type.
  • JSON: oggetti, array, stringhe, numeri, true, false, null. Niente commenti.
  • Stateless in pratica: il token viaggia in ogni richiesta, il server non ricorda chi sei.
  • Cache-Control realizza il vincolo cache.
Il libro della biblioteca nel database è la risorsa; il JSON è una sua rappresentazione. Lo stesso libro potrebbe essere servito come XML o come pagina HTML (negoziazione del contenuto con Accept). Il token Bearer, spesso un JWT, contiene o identifica l'utente: è ciò che rende possibile l'autenticazione senza sessione lato server. Errori JSON tipici: virgolette singole, virgola dopo l'ultimo elemento, chiavi senza virgolette. Sono validi in JavaScript, non in JSON.

Quanto è REST la tua API?

Metti in ordine i livelli di maturità, dal più basso

  1. Livello 0: un solo URL, tutto in POST, come in SOAP
  2. Livello 1: un URI per ogni risorsa
  3. Livello 2: metodi HTTP e codici di stato usati correttamente
  4. Livello 3: le risposte contengono i link alle azioni possibili (HATEOAS)

Fielding, 2008: «Se il motore dello stato dell'applicazione non è guidato dall'ipertesto, allora non può essere RESTful e non può essere un'API REST. Punto.»

È il modello di maturità di Leonard Richardson, presentato nel 2008 e reso famoso da un articolo di Martin Fowler del 2010. La maggior parte delle API pubbliche si ferma al livello 2: in senso stretto, per Fielding, non sono REST ma "HTTP API". La frase di Fielding viene dal suo blog, nell'articolo "REST APIs must be hypertext-driven" (ottobre 2008); traduzione nostra. Esempio di livello 3: la risposta di GET /libri/3 contiene "links": {"prestito": "/libri/3/prestiti"} solo se il libro è disponibile. Il client non deve conoscere gli URI in anticipo: li scopre, come un utente che clicca.

Al computer · 25 minuti

Progetta BiblioAPI

La biblioteca della scuola vuole un'API per i libri e per i prestiti. In un file biblioapi-design.md scrivi una tabella con: metodo, URI, corpo della richiesta, codici di risposta possibili.

  1. Leggere tutti i libri, uno solo, quelli di un autore.
  2. Aggiungere, sostituire ed eliminare un libro.
  3. Prestare un libro e restituirlo.
  4. Scrivi l'esempio JSON di un libro e di un errore.
Controllo: almeno 8 righe. POST /api/libri → 201 o 400. DELETE /api/libri/{id} → 204 o 404. Il prestito di un libro già prestato → 409. Nessun verbo dentro gli URI.
Il file .md si apre con qualsiasi editor; chi non conosce Markdown può usare un .txt con le colonne separate da |. Soluzione di riferimento: GET /api/libri (200); GET /api/libri/{id} (200, 404); GET /api/libri?autore=Calvino (200, anche con array vuoto); POST /api/libri (201 + Location, 400); PUT /api/libri/{id} (200, 400, 404); DELETE /api/libri/{id} (204, 404); POST /api/libri/{id}/prestiti con {"studente": "..."} (201, 404, 409 se già in prestito); DELETE /api/prestiti/{id} oppure PUT /api/prestiti/{id} con {"restituito": true} (204/200, 404). La restituzione si presta a discussione: è una cancellazione del prestito o una modifica del suo stato? Entrambe difendibili, la seconda conserva lo storico. Conservare il file: nella lezione 9 lo implementiamo.

Ponti verso oggi

Le API dell'intelligenza artificiale sono REST

POST https://api.anthropic.com/v1/messages
x-api-key: LA_TUA_CHIAVE  (mai nel codice)
anthropic-version: 2023-06-01
content-type: application/json

{ "model": "nome-del-modello",
  "max_tokens": 300,
  "messages": [ { "role": "user",
    "content": "Spiega REST in due righe" } ] }

Oggi

Un chatbot dentro un'app è quasi sempre una richiesta POST con JSON verso l'API di un modello linguistico. La risposta è un JSON con il testo generato. Stateless: a ogni chiamata si rimanda tutta la conversazione.

Oggi

Con OpenAPI un'API si descrive in un file YAML o JSON. Gli agenti AI leggono descrizioni come queste per decidere quale endpoint chiamare e con quali parametri.

Il formato è quello della Messages API di Anthropic (header x-api-key e anthropic-version); quelli di altri fornitori sono molto simili. Al posto di "nome-del-modello" va l'identificativo di un modello preso dalla documentazione ufficiale. Non mostrare mai una chiave vera: chi la ottiene spende a nome tuo. Notare la statelessness: il modello non ricorda nulla tra una chiamata e l'altra; l'app rimanda ogni volta l'intera lista di messaggi. Spunto critico: "POST /v1/messages" è REST? È una risorsa su cui si crea qualcosa, ma somiglia molto a una chiamata di procedura remota (lezione 2). OpenAPI nasce da Swagger, donato nel 2015 alla OpenAPI Initiative della Linux Foundation; la versione 3.1 (2021) usa JSON Schema, lo stesso linguaggio con cui si descrivono gli strumenti che un modello può chiamare (tool use) e i tool dei server MCP (Model Context Protocol).
