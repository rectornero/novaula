Kernel e shell

Il nocciolo che comanda l'hardware e il guscio con cui gli parli. Oggi apriamo la finestra nera dei comandi, su Windows e su un Linux che gira nel browser.

Obiettivi: distinguere kernel e shell; conoscere i tipi di kernel (monolitico, microkernel, ibrido); capire che cos'è una chiamata di sistema; usare i comandi di base di cmd, PowerShell e della shell Linux; confrontare interfacce a riga di comando e grafiche; conoscere le pipe. Durata indicativa: 2 ore. Servono: PC Windows con Prompt dei comandi e PowerShell non bloccati dalle policy della scuola; accesso a bellard.org/jslinux (provarlo prima dalla rete della scuola; alternativa copy.sh/v86 o demo alla LIM).

Due parole da una noce

Il nocciolo e il guscio

kernel

Il nocciolo

La parte del sistema operativo che parla direttamente con l'hardware: gestisce processi, memoria, file system, driver. Resta in memoria dall'accensione allo spegnimento.

shell

Il guscio

Il programma che fa da interfaccia tra te e il kernel: legge i tuoi comandi, li interpreta, chiede al kernel di eseguirli e ti mostra il risultato. Può essere a riga di comando o grafica.

La shell è un programma come gli altri: si può chiudere e sostituire. Il kernel no: se si ferma lui, si ferma tutto.
Il termine "shell" nasce negli anni '60 nel progetto Multics: lo usò Louis Pouzin per il programma che interpretava i comandi. Esempi di shell: cmd.exe, PowerShell, bash e zsh (Linux, macOS), sh di BusyBox (Alpine); anche Esplora risorsi di Windows (explorer.exe) è la shell grafica. Prova pratica alla LIM: chiudere explorer.exe da Gestione attività fa sparire barra e desktop, ma i programmi aperti continuano a funzionare; si riavvia con File, Esegui nuova attività, explorer.

Il kernel

Tutto dentro o quasi niente dentro?

TipoIdeaEsempi
MonoliticoTutti i servizi (driver, file system, rete) nel kernel: veloce, ma un errore in un driver può bloccare tuttoLinux (con moduli caricabili), i primi Unix
MicrokernelNel kernel solo l'essenziale; driver e file system sono processi separati: più robusto, un po' più lentoMinix 3, QNX (auto, macchinari)
IbridoStruttura a moduli ispirata al microkernel, ma molti servizi restano nel kernel per velocitàWindows (NT), macOS e iOS (XNU)
Nel 1992 Andrew Tanenbaum (autore di Minix) e Linus Torvalds discussero pubblicamente su Usenet proprio di questo: "Linux è obsoleto" perché monolitico, scriveva Tanenbaum. Ne riparleremo nella lezione sui sistemi in commercio. I "moduli" di Linux sono pezzi di kernel (spesso driver) caricati quando servono: restano però dentro il kernel. QNX è usato nei sistemi di bordo di molte automobili.

Chiamate di sistema

Un programma non scrive sul disco: lo chiede

// Java: scrivo una riga in un file
FileWriter f = new FileWriter("nota.txt");
f.write("ciao kernel");
f.close();

// sotto, la JVM chiede al kernel:
open("nota.txt") → write(…) → close()

Una chiamata di sistema (system call) è la richiesta formale di un programma al kernel: aprire un file, creare un processo, chiedere memoria, usare la rete.

Linux ne ha alcune centinaia; Windows le nasconde dietro le sue API (per esempio WriteFile).

Su Linux i nomi reali sono proprio open (o openat), write, close; su Windows la catena è WriteFile (API Win32) → NtWriteFile (ntdll) → kernel. Il programmatore Java non le vede: le usa la JVM. Domanda: perché non lasciare che i programmi scrivano direttamente sul disco? Perché due programmi potrebbero scrivere sugli stessi blocchi e distruggere i file, e un programma malevolo potrebbe leggere tutto. Lo approfondiamo nella lezione su user mode e kernel mode.

Puzzle

Scrivi dir e premi Invio: che cosa succede, in ordine?

  1. La shell legge la riga che hai scritto
  2. La shell riconosce il comando dir
  3. La shell fa una chiamata di sistema per leggere la cartella
  4. Il kernel, con il file system e il driver del disco, trova i nomi dei file
  5. Il kernel restituisce l'elenco alla shell
  6. La shell scrive l'elenco nella finestra
Ordine corretto come scritto. Molti mettono il kernel prima della shell: ricordare che è la shell a ricevere i tasti (tramite il kernel e il driver della tastiera, a voler essere precisi) e a decidere che cosa chiedere. Anche l'ultima fase, scrivere sullo schermo, passa dal sistema operativo. dir in cmd è un comando interno della shell; in Linux ls è invece un programma separato, in /bin.

Mettiti alla prova

Esplora file di Windows (explorer.exe) è…

  1. Il kernel di Windows
  2. Una shell, cioè un'interfaccia grafica
  3. Il driver del disco
  4. Una parte del firmware UEFI

explorer.exe è la shell grafica di Windows: disegna desktop, barra delle applicazioni e finestre delle cartelle, e chiede al kernel di leggere e spostare i file. Il kernel (ntoskrnl.exe) non ha finestre. Se chiudi explorer.exe, i programmi aperti continuano a funzionare.

Tranello: "shell" fa pensare solo alla finestra nera. Ogni interfaccia che traduce le azioni dell'utente in richieste al kernel è una shell, anche quella grafica. Se il tempo lo permette, mostrare alla LIM la prova di chiudere e riavviare explorer.exe (vedi note della slide 3).

Al computer · 15 minuti

Primi comandi nel Prompt

  1. Premi Win + R, scrivi cmd, Invio. Prova uno alla volta: ver, hostname, whoami.
  2. Scrivi cd %USERPROFILE%\Documents, poi mkdir prova-shell e cd prova-shell.
  3. Crea un file: echo ciao kernel > nota.txt, poi type nota.txt e dir.
  4. Scrivi tasklist, poi tasklist | find /i "explorer".
  5. Copia i comandi con le risposte in Writer: prompt-cognome.odt.
Controllo: whoami risponde nel formato computer\utente; dir mostra nota.txt da 14 byte (12 caratteri più a capo); l'ultimo comando mostra una sola riga con explorer.exe e il suo PID.
ver risponde "Microsoft Windows [Versione 10.0.xxxxx]": anche Windows 11 dice 10.0 (si distingue dal numero di build, 22000 o più): lo usiamo nella lezione sui sistemi in commercio. echo ciao kernel > nota.txt scrive "ciao kernel" più lo spazio prima di > più CR LF: 11 + 1 + 2 = 14 byte. Se scrivono echo ciao kernel>nota.txt (senza spazio) sono 13 byte: buona occasione per osservare che ogni carattere conta. Per selezionare il testo nella console: trascinare con il mouse e premere Invio o Ctrl+C. Se cmd è bloccato, usare PowerShell: tutti questi comandi funzionano anche lì tranne find, che si sostituisce con findstr.

Due interfacce

Mouse o tastiera?

Interfaccia grafica (GUI)

  • Facile da imparare: vedi le opzioni
  • Comoda per immagini, layout, navigazione
  • Lenta da ripetere 100 volte
  • Difficile da automatizzare

Riga di comando (CLI)

  • Devi conoscere i comandi
  • Veloce e precisa: un comando, mille file
  • Si salva in uno script e si ripete
  • Funziona anche a distanza, sui server senza schermo

Le prime GUI: Xerox Alto (1973), Apple Macintosh (1984), Windows 1.0 (1985). Prima c'era solo la riga di comando.

Esempio concreto: rinominare 300 foto della gita aggiungendo la data. Con la GUI una alla volta; con PowerShell una riga sola. Quasi tutti i server di internet (Linux) non hanno interfaccia grafica e si amministrano via SSH dalla shell. Il Macintosh si ispirò all'interfaccia sviluppata allo Xerox PARC.

Puzzle

Stesso lavoro, due shell: abbina cmd e Linux

dir
ls (elenca i file della cartella)
type nota.txt
cat nota.txt (mostra il contenuto)
cls
clear (pulisce lo schermo)
tasklist
ps (elenca i processi)
copy a.txt b.txt
cp a.txt b.txt (copia un file)
del a.txt
rm a.txt (cancella senza Cestino)
Sfida a squadre: 90 secondi, poi verifica. Curiosità: cd e mkdir hanno lo stesso nome in entrambe. In PowerShell funzionano sia dir sia ls, sia type sia cat: sono alias di Get-ChildItem e Get-Content, aggiunti apposta per chi viene da cmd o da Linux. Attenzione a del e rm: i file non vanno nel Cestino.

Al computer · 15 minuti

PowerShell: i processi come oggetti

  1. Apri Windows PowerShell dal menu Start (non serve l'amministratore).
  2. Conta i processi: (Get-Process).Count
  3. I 5 che usano più memoria: scrivi su una sola riga il comando qui sotto.
  4. Prova anche ls e Get-Alias ls: chi c'è dietro?
  5. Aggiungi comandi e risultati al file prompt-cognome.odt.
Controllo: il conteggio è simile a quello di Gestione attività (centinaia). WS è la memoria in byte: 524 288 000 sono 500 MB. Get-Alias ls risponde Get-ChildItem.
Get-Process | Sort-Object WS -Descending | Select-Object -First 5 Name, Id, WS
WS = Working Set, la memoria fisica usata dal processo, in byte: per avere MB dividere per 1024 × 1024 (1 048 576); 524 288 000 / 1 048 576 = 500. Il simbolo | è la pipe: l'uscita di un comando diventa l'ingresso del successivo (slide seguente). Differenza chiave: cmd e la shell Linux passano testo, PowerShell passa oggetti con proprietà (Name, Id, WS), per questo si può ordinare per WS senza tagliare colonne di testo. Per digitare | sulla tastiera italiana: Maiusc + il tasto \ a sinistra dell'1.

Menti che ci hanno preceduto

Piccoli comandi, uniti da una pipe

La pipe | collega l'uscita di un comando all'ingresso del successivols /bin | wc -l
Traduzione nostra di "Make each program do one thing well", primo punto delle massime della filosofia Unix nella prefazione "UNIX Time-Sharing System: Foreword" (BSTJ, vol. 57, n. 6, 1978). Fu McIlroy a proporre le pipe, aggiunte a Unix nel 1973. Il comando del riquadro: ls elenca i file di /bin, wc -l conta le righe: in tutto, quanti comandi ci sono in /bin. Lo proviamo nel prossimo laboratorio. Esempio Windows già visto: tasklist | find /i "explorer".

Al computer · 20 minuti

Un Linux vero, dentro il browser

  1. Vai su bellard.org/jslinux e avvia la console Alpine Linux (x86). Aspetta il prompt localhost:~#.
  2. Il kernel: uname -r e cat /proc/version.
  3. La shell: echo $0. I processi: ps.
  4. Le pipe: ls /bin | wc -l, poi ps | wc -l.
  5. Annota comandi e risposte in prompt-cognome.odt, con uno screenshot.
Controllo: /proc/version inizia con Linux version; ps mostra pochi processi (meno di 20), tra cui il PID 1. Confronta con le centinaia di Windows: è un sistema minimo.
JSLinux (Fabrice Bellard) emula un PC dentro il browser: nessun account, nessuna installazione, ricaricando la pagina tutto si azzera. Alpine usa BusyBox: molti comandi (ls, ps, wc) sono un unico programma con tanti nomi; echo $0 risponde -sh (la shell ash di BusyBox). /proc non è una cartella vera sul disco: è il kernel che mostra le sue informazioni come se fossero file (astrazione!). ps | wc -l conta anche la riga di intestazione. Se il sito è bloccato o lento: demo alla LIM, oppure copy.sh/v86 con un'immagine Linux.

Quiz a trabocchetto

Il programma Java scrive "nota.txt". Chi tocca davvero il disco?

  1. Il programma Java, con l'istruzione write
  2. La Java Virtual Machine
  3. La shell da cui hai avviato il programma
  4. Il kernel, tramite il file system e il driver del disco

Programma e JVM girano in modalità utente e possono solo chiedere, con una chiamata di sistema. La shell ha solo avviato il programma e non c'entra più. È il kernel, con il file system e il driver, a decidere i blocchi e a dare i comandi al controller del disco.

Tranello A: "write" sembra scrivere davvero. Tranello B: la JVM sembra il "sistema" del programma Java, ma è anch'essa un processo utente. Tranello C: molti pensano che la shell resti "in mezzo" a tutto. Ponte verso la prossima lezione: modalità utente e modalità kernel.

Kernel e shell oggi

Due novità di questi anni

Oggi

L'AI nella shell

Gli assistenti di programmazione basati su modelli linguistici lavorano anche nel terminale: leggono i file del progetto, propongono comandi e chiedono il permesso prima di eseguirli. La regola resta la tua: non approvare un comando che non capisci.

Oggi

Un nuovo linguaggio nel kernel

Il kernel Linux è scritto quasi tutto in C. Dalla versione 6.1 (dicembre 2022) accetta anche codice in Rust, un linguaggio che impedisce molti errori di memoria: in un kernel, un errore così può bloccare tutto o aprire una falla.

Esempi di assistenti nel terminale: Claude Code, GitHub Copilot CLI, Gemini CLI; tutti richiedono un account e sono pensati per professionisti: eventuale demo solo del docente alla LIM. Domanda: un comando come rm -rf o del /s proposto da un'AI va eseguito "a fiducia"? No: la shell esegue con i permessi dell'utente, chi approva ne è responsabile. Sul Rust: il supporto iniziale è stato unito nella versione 6.1; oggi alcuni driver sono scritti in Rust.
