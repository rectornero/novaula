da Java e JSP

Il server c'è. Ora dall'altra parte del filo: un programma Java che chiama BiblioAPI e una pagina JSP che trasforma il suo JSON in una pagina web.

5G TPSIHttpClient, POST, errori di rete, chiamate asincrone, JSP su Tomcat

Obiettivi: usare java.net.http.HttpClient (Java 11+) per GET e POST, leggere codice di stato, header e corpo; distinguere un errore HTTP (404, 500) da un errore di rete (eccezione); fare chiamate asincrone con sendAsync; realizzare una pagina JSP su Tomcat che consuma l'API lato server, con l'escape dell'output. Durata indicativa: 4 ore. Prerequisiti: il BiblioServer della lezione 9 acceso sulla porta 8000. Software: JDK 21; Apache Tomcat 10.1 o successivo (pacchetti jakarta.*), distribuito come zip, non serve installarlo. Fallback se Tomcat non è disponibile: il docente mostra la parte JSP sulla LIM, e gli studenti fanno la variante "ClientHtml" descritta nelle note del laboratorio 3.

Per cominciare

Una pagina deve mostrare i libri di BiblioAPI. Chi dovrebbe chiamare l'API?

  1. Il browser, con JavaScript
  2. Il server web, che poi manda l'HTML pronto
  3. Dipende da chi deve vedere i dati
  4. Non importa, è uguale
Sondaggio senza risposta giusta, che regge tutta la lezione. Oggi facciamo la chiamata lato server (JSP), nella lezione 12 lato browser (fetch). Argomenti da far emergere: lato server la chiave o la password dell'API restano nascoste e non serve il CORS; il browser riceve HTML già pronto, utile per i motori di ricerca. Lato browser la pagina si aggiorna senza ricaricarsi e il server web lavora meno. La D è l'unica davvero sbagliata: cambiano sicurezza, prestazioni e chi vede che cosa.

Il client del JDK

Una GET in tre oggetti

import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.regex.*;

public class ClientBiblio {
  public static void main(String[] args) throws Exception {
    HttpClient client = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(3)).build();
    HttpRequest get = HttpRequest.newBuilder(URI.create("http://localhost:8000/api/libri"))
        .header("Accept", "application/json").GET().build();
    HttpResponse<String> r = client.send(get, HttpResponse.BodyHandlers.ofString());
    System.out.println("Stato: " + r.statusCode());
    Matcher m = Pattern.compile("\"titolo\":\"([^\"]*)\"").matcher(r.body());
    while (m.find()) System.out.println("- " + m.group(1));
  }
}
Tre oggetti: HttpClient (si crea una volta e si riusa: gestisce le connessioni, HTTP/1.1 e HTTP/2, i redirect se configurati), HttpRequest (immutabile, si costruisce con il builder), HttpResponse (codice, header, corpo). BodyHandlers.ofString() dice di leggere il corpo come stringa; esistono ofFile, ofLines, ofInputStream. L'espressione regolare che estrae i titoli è fragile: si rompe se il server cambia l'ordine o la spaziatura dei campi. Va bene per il laboratorio; in un progetto si usa Jackson o Gson (ObjectMapper.readValue(r.body(), Libro[].class)). Il codice è provato con JDK 21 contro il BiblioServer della lezione 9.

Il punto chiave del passo 5: per HttpClient un 404 o un 500 è una risposta valida, non un errore. Tocca al programma controllare statusCode(). Se le lettere accentate escono male nella console di Windows, eseguire prima chcp 65001 oppure lanciare java -Dstdout.encoding=UTF-8 ClientBiblio.java (Java 19+).

Puzzle

Abbina ogni pezzo del client al suo compito

HttpClient
Si crea una volta e si riusa: gestisce le connessioni
HttpRequest
Immutabile: URI, metodo, header, corpo
BodyPublishers.ofString
Trasforma una stringa nel corpo della richiesta
BodyHandlers.ofString
Dice come leggere il corpo della risposta
sendAsync
Restituisce subito un CompletableFuture
Lavoro a coppie, 2 minuti. Domanda di approfondimento: perché è sbagliato creare un nuovo HttpClient per ogni richiesta in un ciclo? (Ogni client ha il suo pool di connessioni e i suoi thread: crearne mille spreca risorse e impedisce il riuso delle connessioni keep-alive.)

Inviare dati

POST con JSON, e un limite di tempo

String json = """
    {"titolo":"Lessico famigliare","autore":"Natalia Ginzburg","anno":1963}""";
HttpRequest post = HttpRequest.newBuilder(URI.create(BASE))
    .header("Content-Type", "application/json")
    .timeout(Duration.ofSeconds(5))
    .POST(HttpRequest.BodyPublishers.ofString(json))
    .build();
try {
  HttpResponse<String> c = client.send(post, HttpResponse.BodyHandlers.ofString());
  System.out.println(c.statusCode() + " " + c.headers().firstValue("Location").orElse("-"));
} catch (java.net.ConnectException e) {
  System.out.println("BiblioAPI non raggiungibile: il server è acceso?");
} catch (java.net.http.HttpTimeoutException e) {
  System.out.println("Nessuna risposta entro 5 secondi");
}
Il text block (tre virgolette, Java 15+) evita di scrivere \" per ogni virgoletta. BASE è la costante "http://localhost:8000/api/libri". Due tempi diversi: connectTimeout sul client (tempo massimo per aprire la connessione, eccezione HttpConnectTimeoutException) e timeout sulla richiesta (tempo massimo per avere la risposta, HttpTimeoutException). Senza timeout un client può restare appeso per sempre a un server bloccato: in un sistema distribuito è uno dei guasti più comuni (lezione 1 dell'unità). Domanda: se scatta il timeout del POST, il libro è stato creato? (Non lo sappiamo: il server potrebbe averlo salvato. Ripetere un POST non è sicuro, perché non è idempotente.)

Quiz a trabocchetto

Il server è spento. Che cosa succede a client.send(get, …)?

  1. Restituisce una risposta con codice 404
  2. Lancia una ConnectException: non c'è nessun codice di stato
  3. Restituisce una risposta con codice 503
  4. Restituisce null

Un codice di stato può mandarlo solo un server che risponde. Se nessuno ascolta sulla porta, la connessione TCP viene rifiutata e HttpClient lancia un'eccezione. 503 lo manda un server (o un proxy) acceso che non può servire la richiesta.

Il tranello è la C: "servizio non disponibile" suona giusto, ma deve essere qualcuno a dirlo. Se davanti al server ci fosse un proxy o un API gateway acceso, allora il client riceverebbe davvero 502 o 503 dal proxy: è il vincolo "sistema a livelli" della lezione 8. Provato con JDK 21: a server spento compare java.net.ConnectException. Tre famiglie di problemi da distinguere nei client: errori di rete (eccezioni), errori del client (4xx), errori del server (5xx).

  3. Se il codice è 4xx o 5xx, stampa Errore seguito dal corpo della risposta.

Controllo: a server acceso: 201 /api/libri/4 e poi il JSON di Lessico famigliare. Riesegui: /api/libri/5. A server spento: BiblioAPI non raggiungibile: il server è acceso? e nessuno stack trace.
Per il passo 2: URI nuovo = URI.create(BASE).resolve(location), perché Location contiene un percorso relativo (/api/libri/4) e resolve lo combina con schema, host e porta di BASE. Per il passo 3: if (c.statusCode() >= 400) System.out.println("Errore " + c.statusCode() + ": " + c.body()). Fa' notare che la prima GET deve stare anch'essa nel try, altrimenti a server spento l'eccezione arriva da lì. Senza aspettare

Più richieste insieme con sendAsync

var f1 = client.sendAsync(richiesta("/1"),
                 BodyHandlers.ofString());
var f2 = client.sendAsync(richiesta("/2"),
                 BodyHandlers.ofString());
// qui il programma può fare altro
String t1 = f1.thenApply(HttpResponse::body).join();
String t2 = f2.thenApply(HttpResponse::body).join();
System.out.println(t1 + "\n" + t2);
  • send blocca il thread finché la risposta non arriva.
  • sendAsync torna subito con un CompletableFuture: le richieste viaggiano in parallelo.
  • thenApply dice che cosa fare con la risposta; join aspetta il risultato.
  • Tempo totale ≈ quello della risposta più lenta, non la somma.
richiesta(p) è un piccolo metodo che costruisce HttpRequest.newBuilder(URI.create(BASE + p)).build(). È lo stesso modello delle Promise di JavaScript che useremo nella lezione 12 (then, await). Esperimento con il quiz della lezione 9: 200 POST con sendAsync, poi una GET dell'elenco: con ConcurrentHashMap e AtomicInteger gli id sono tutti diversi; con HashMap e int++ capita di perdere libri. Collegamento con la lezione 2 sulle RPC sincrone e asincrone.

JavaServer Pages

HTML con dentro un po' di Java, eseguito sul server

Direttiva

<%@ page import="…" %>

Impostazioni della pagina: import, codifica.

Scriptlet

<% codice Java %>

Istruzioni eseguite a ogni richiesta.

Espressione

<%= valore %>

Il valore finisce nell'HTML.

Alla prima richiesta Tomcat traduce la JSP in una servlet Java e la compila. Il browser non vede mai il Java: riceve solo l'HTML prodotto.

Nei progetti veri il Java sta in una servlet e la JSP mostra soltanto i dati (modello MVC). Per il laboratorio basta una pagina.

Il traduttore di Tomcat si chiama Jasper; i file generati stanno in work/Catalina/localhost/<app>/org/apache/jsp, ed è istruttivo aprirli. Esiste anche la dichiarazione <%! … %> per campi e metodi della servlet: la usiamo per un HttpClient condiviso e per la funzione di escape. Da Tomcat 10 i pacchetti sono jakarta.servlet.* e non più javax.servlet.*: una vecchia guida trovata in rete può non funzionare. JSP è una tecnologia matura, oggi usata soprattutto in applicazioni aziendali esistenti; il libro di testo la usa perché mostra bene il rendering lato server.

La pagina della biblioteca

libri.jsp: l'API dentro una tabella

<%@ page contentType="text/html; charset=UTF-8" import="java.net.URI, java.net.http.*, java.util.regex.*" %>
<%! static final HttpClient CLIENT = HttpClient.newHttpClient();
    static String html(String s) {
      return s.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;").replace("\"", "&quot;");
    } %>
<% HttpRequest req = HttpRequest.newBuilder(URI.create("http://localhost:8000/api/libri")).build();
   HttpResponse<String> r = CLIENT.send(req, HttpResponse.BodyHandlers.ofString());
   Matcher m = Pattern.compile("\"titolo\":\"([^\"]*)\",\"autore\":\"([^\"]*)\",\"anno\":(\\d+)").matcher(r.body()); %>
<!doctype html>
<html lang="it"><head><meta charset="utf-8"><title>Biblioteca</title></head><body>
<h1>Libri della biblioteca</h1>
<table border="1"><tr><th>Titolo</th><th>Autore</th><th>Anno</th></tr>
<% while (m.find()) { %>
  <tr><td><%= html(m.group(1)) %></td><td><%= html(m.group(2)) %></td><td><%= m.group(3) %></td></tr>
<% } %>
</table><p>Risposta dell'API: <%= r.statusCode() %></p></body></html>
La pagina gira sul server Tomcat (porta 8080) e chiama BiblioAPI (porta 8000): sono due server diversi sulla stessa macchina, un piccolo sistema distribuito. L'oggetto HttpClient è nella dichiarazione <%! %>, quindi è condiviso tra tutte le richieste: va bene, perché HttpClient è thread-safe. L'espressione regolare si appoggia sull'ordine dei campi prodotto dal nostro server (titolo, autore, anno): è un accoppiamento forte, ed è proprio ciò che una libreria JSON evita. La funzione html() fa l'escape dei caratteri speciali dell'HTML: senza, un titolo pieno di tag verrebbe eseguito dal browser (quiz successivo). Con JSTL si scriverebbe <c:out value="${titolo}"/>, che fa l'escape da sola, ma servono i jar di Jakarta Standard Tag Library nella cartella WEB-INF/lib.

Mettiti alla prova

Qualcuno aggiunge un libro con titolo <script>alert(1)</script>. La JSP senza html()…

  1. Mostra il titolo così com'è, come testo
  2. Dà errore di compilazione
  3. Non fa niente: il JSON non può contenere tag
  4. Manda lo script al browser, che lo esegue

È un Cross-Site Scripting memorizzato: il dato arriva da un'API, ma la JSP lo copia nell'HTML e il browser di chiunque apra la pagina esegue lo script. L'escape trasforma < in &lt; e il titolo torna testo innocuo.

Collegamento con l'Unità 1 (Network e Web App Security, OWASP Top 10: Injection). Il punto importante: anche i dati che arrivano da un nostro servizio vanno trattati come non fidati quando finiscono in un altro contesto (HTML, SQL, comandi). La C è il tranello: una stringa JSON può contenere qualsiasi carattere, tag compresi. Si può provare in laboratorio, solo sul proprio server locale: un POST con quel titolo e poi la pagina senza escape. Ricordare di non provarlo mai su sistemi altrui.

BiblioAPI in una pagina web, con Tomcat

  1. Estrai lo zip di Tomcat 10.1 in C:\tomcat (o nella cartella indicata dal docente).
  2. Crea la cartella webapps\biblio e dentro il file libri.jsp della slide.
  3. Avvia Tomcat con bin\startup.bat e BiblioServer sulla porta 8000.
  4. Apri http://localhost:8080/biblio/libri.jsp.
  5. Aggiungi con curl un libro con titolo <b>Prova</b> e ricarica la pagina.
Controllo: una tabella con i libri e in fondo Risposta dell'API: 200. Il libro nuovo appare con il testo <b>Prova</b> scritto per intero, non in grassetto: l'escape funziona. Con "Visualizza sorgente" non c'è traccia del Java.
Tomcat richiede la variabile JAVA_HOME (o JRE_HOME) che punta al JDK: set JAVA_HOME=C:\Program Files\Java\jdk-21 nel Prompt prima di startup.bat. Se la porta 8080 è occupata, cambiarla in conf\server.xml (Connector port). Spegnere Tomcat con bin\shutdown.bat. Fallback senza Tomcat: scrivere ClientHtml.java, che fa la stessa GET e scrive con Files.writeString un file libri.html con la tabella (usando la stessa funzione html()); aprendo il file nel browser si vede lo stesso risultato. Il rendering avviene comunque lato "server", cioè nel programma Java.

Puzzle per l'esame

Il browser chiede libri.jsp: metti in ordine

  1. Il browser invia GET /biblio/libri.jsp a Tomcat
  2. Tomcat traduce e compila la JSP in una servlet, se è la prima volta
  3. La servlet invia GET /api/libri a BiblioAPI
  4. BiblioAPI risponde 200 con l'array JSON
  5. La servlet scrive le righe della tabella con l'escape
  6. Tomcat risponde al browser 200 con l'HTML
È esattamente il diagramma di sequenza che si chiede di disegnare in una prova di progetto: quattro "attori" (browser, Tomcat, BiblioAPI e, in un progetto vero, il database dietro BiblioAPI). Far disegnare il diagramma alla lavagna con le frecce numerate e le porte (8080, 8000). Domanda: il browser sa che esiste BiblioAPI? (No: vede solo Tomcat. Per questo la chiave di un'API a pagamento può stare al sicuro sul server.)

Menti che ci hanno preceduto

Un livello in più: Tomcat tra il browser e l'API

Il livello in più

La JSP sta in mezzo: il browser non sa che BiblioAPI esiste, e l'API non sa nulla del browser.

Il prezzo

Un salto di rete in più, un server in più da tenere acceso, un punto in più dove qualcosa può guastarsi.

La frase è attribuita a David Wheeler (1927-2004), che lavorò all'EDSAC di Cambridge e a cui si deve la "Wheeler jump", la prima tecnica di chiamata di subroutine. Butler Lampson la cita attribuendola a lui; non esiste un testo scritto di Wheeler con questa frase, per questo diciamo "attribuita". Traduzione nostra di "All problems in computer science can be solved by another level of indirection". Spesso si aggiunge la seconda parte: "…tranne il problema di avere troppi livelli di indirezione". Collegamenti: il vincolo "sistema a livelli" di REST (lezione 8), l'API gateway e l'ESB (lezione 3), e il proxy che custodisce la chiave dell'API nella prossima slide.

Oggi

Per un'app che usa l'AI, il modello è un web service come BiblioAPI: lo stesso HttpClient, un POST con JSON. La chiave si legge da una variabile d'ambiente e resta sul server, mai nel codice o su GitHub.

Oggi

Generare l'HTML sul server, come fa la JSP, è tornato centrale: framework moderni come Next.js lo fanno per pagine più veloci e più leggibili dai motori di ricerca.

Non eseguire il codice senza una chiave del docente: serve un account a pagamento del fornitore e la chiave non va mai condivisa con gli studenti. corpoJson è il JSON con model, max_tokens e messages visto nella lezione 8. Se una chiave finisce per sbaglio in un repository pubblico, va revocata subito: esistono bot che scandiscono GitHub in cerca di chiavi. Sul secondo box: il rendering lato server non è mai sparito, ma per qualche anno le single page application lo avevano messo in secondo piano; oggi molti framework mescolano le due cose.
