Unità 3 · Applicazioni Java per la comunicazione in rete

La chat
con i socket TCP

Un server, tanti client, un thread per ciascuno e un piccolo protocollo di testo: costruiamo da zero la stessa idea che sta dietro a ogni app di messaggi.

Lezione di laboratorio, 3-4 ore. Obiettivi: ripassare Socket e ServerSocket; capire perché un server a thread singolo serve un client alla volta; scrivere un server multi-client con un thread per client; progettare un protocollo di testo; gestire correttamente la disconnessione; riflettere sulla sicurezza (testo in chiaro, TLS). Porta usata: 5000 (deve essere libera e, per le prove tra PC diversi, aperta nel firewall del PC che fa da server: altrimenti si lavora tutti su 127.0.0.1).

Una storia del 1971

Il primo messaggio tra due computer in rete

1971, BBN, Cambridge (USA). Ray Tomlinson manda un messaggio tra due computer PDP-10 collegati ad ARPANET, uno accanto all'altro. Per separare utente e computer sceglie il simbolo @.

1988, Università di Oulu (Finlandia). Jarkko Oikarinen crea IRC: canali, nickname e comandi di testo come NICK e PRIVMSG.

Originale: "The test messages were entirely forgettable and I have, therefore, forgotten them." Dalla pagina di Ray Tomlinson sul sito di BBN; traduzione nostra. Il primo messaggio NON era "QWERTYUIOP" con certezza: Tomlinson disse che probabilmente era qualcosa del genere. La @ fu scelta perché era sulla tastiera e non compariva nei nomi. IRC è descritto nella RFC 1459 (1993). Il protocollo che inventeremo oggi somiglia molto a IRC: comandi di testo, una riga per messaggio.

Ripasso veloce

Socket TCP: che cosa ci dà e che cosa no

ServerSocket

Ascolta su una porta. accept() si blocca finché arriva un client e restituisce un nuovo Socket per parlare con lui.

Socket

Un capo della connessione: indirizzo IP + porta. Da qui prendi un InputStream e un OutputStream.

Niente messaggi

TCP è un flusso di byte affidabile e ordinato. Dove finisce un messaggio lo decide il nostro protocollo: noi useremo una riga.

Nella lezione su Claude Code un agente correggeva ServerChat.java e GestoreClient.java. Oggi quei file li scriviamo noi, e capiamo da dove veniva quel bug.
Collegamento con il deck claude-code: l'esempio "il server della chat si blocca quando un client si disconnette" era causato da un'eccezione di readLine() non gestita. Oggi la eviteremo con try/finally. Ricordare il three-way handshake (SYN, SYN-ACK, ACK) visto in Sistemi e reti: lo fa il sistema operativo, Java ci mostra solo il risultato. TCP non preserva i confini: due println possono arrivare in un solo read() o un println in due; BufferedReader.readLine() ricompone le righe.

Puzzle

Metti in ordine la vita di una connessione

  1. Il server crea new ServerSocket(5000)
  2. Il server chiama accept() e si blocca
  3. Il client crea new Socket(host, 5000): parte l'handshake TCP
  4. accept() restituisce un Socket nuovo per quel client
  5. Client e server si scambiano righe di testo
  6. Il client chiude: sul server readLine() restituisce null
Il passo 3 prima del 2 è un errore comune: se il server non è ancora in ascolto, il client riceve "Connection refused". Far notare che il Socket restituito da accept() è diverso dal ServerSocket: il ServerSocket continua ad ascoltare per altri client. Sul server, la porta locale del nuovo Socket è sempre 5000; ciò che distingue le connessioni è la coppia (IP e porta del client).

Il comportamento del secondo client è il tema del quiz successivo: non svelarlo.

Quiz a trabocchetto

ServerEco sta servendo un client. Se ne collega un secondo: che cosa succede?

  1. Riceve subito "Connection refused"
  2. Si connette, ma non riceve risposte finché il primo non esce
  3. I due client vengono serviti a turno, una riga ciascuno
  4. Il server va in errore e si chiude

L'handshake lo completa il sistema operativo, che mette la connessione in coda (backlog). Il server però è bloccato nel while del primo client e chiamerà di nuovo accept() solo quando quel client chiude.

Molti rispondono A: invece la connessione riesce, ed è proprio questo che inganna. Lo abbiamo verificato: il secondo client si collega ma non riceve nulla finché il primo non si disconnette; a quel punto il server legge le righe che il secondo aveva già mandato e risponde. Il backlog si imposta con il secondo argomento di new ServerSocket(porta, backlog). Soluzione: un thread per client.

L'architettura

Un thread per client, una lista condivisa

Ciclo infinito: accept(), poi crea un thread e torna subito ad ascoltare.

GestoreClient anna

GestoreClient bruno

GestoreClient carla

clienti

Un Set thread-safe con tutti i gestori: per inoltrare un messaggio si scorre il Set e si scrive a ognuno.

Ogni GestoreClient legge dal proprio socket in un ciclo bloccante: con un thread per client i blocchi non si disturbano. Il Set è condiviso tra tutti i thread: per questo ConcurrentHashMap.newKeySet() e non un HashSet. Alternativa: CopyOnWriteArraySet, ottimo quando si legge molto e si modifica poco. Domanda: quanti thread ci sono con 3 client? Quattro: il main che fa accept e tre gestori.

Il codice · 2

ServerChat.java

public class ServerChat {
    static final Set<GestoreClient> clienti = ConcurrentHashMap.newKeySet();

    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket(5000)) {
            System.out.println("Chat in ascolto sulla porta 5000");
            while (true) {
                Socket s = server.accept();                  // aspetta un client
                new Thread(new GestoreClient(s)).start();    // un thread per client
            }
        }
    }

    static void inoltra(String riga, GestoreClient mittente) {
        for (GestoreClient c : clienti)
            if (c != mittente) c.invia(riga);
    }
}
Import: java.io.IOException, java.net.*, java.util.Set, java.util.concurrent.ConcurrentHashMap. Qui il Socket NON va in un try-with-resources: lo chiuderà il GestoreClient quando finisce. Con Java 21 basta cambiare una riga per usare i virtual thread: Thread.ofVirtual().start(new GestoreClient(s)); il resto del codice resta identico ed è adatto a migliaia di client.

Il codice · 3

GestoreClient: il cuore del metodo run()

try (s; var in = new BufferedReader(new InputStreamReader(s.getInputStream(), UTF_8))) {
    out = new PrintWriter(s.getOutputStream(), true, UTF_8);
    String riga = in.readLine();                              // 1a riga: NICK nome
    if (riga == null || !riga.matches("NICK \\w{1,16}")) { invia("ERR serve NICK nome"); return; }
    nick = riga.substring(5);
    ServerChat.clienti.add(this);
    invia("OK benvenuto " + nick);
    ServerChat.inoltra("INFO " + nick + " entra nella chat", this);
    while ((riga = in.readLine()) != null && !riga.equals("QUIT")) {
        if (riga.startsWith("MSG ")) ServerChat.inoltra("MSG " + nick + " " + riga.substring(4), this);
        else invia("ERR comando sconosciuto");
    }
} catch (IOException e) {
    System.out.println("Connessione persa: " + e.getMessage());
} finally {                                                   // sempre, anche dopo un errore
    if (ServerChat.clienti.remove(this)) ServerChat.inoltra("INFO " + nick + " esce dalla chat", this);
}
Classe completa: public class GestoreClient implements Runnable { private final Socket s; private PrintWriter out; private String nick; GestoreClient(Socket s) { this.s = s; } synchronized void invia(String riga) { out.println(riga); } @Override public void run() { ...codice della slide... } }. Import: java.io.*, java.net.Socket, static java.nio.charset.StandardCharsets.UTF_8. "try (s; ...)" (Java 9+) chiude anche il socket. invia è synchronized perché più thread possono scrivere allo stesso client nello stesso momento (due messaggi inoltrati insieme): senza, le righe potrebbero mescolarsi. Il finally è la correzione del bug visto con Claude Code: se il client sparisce (rete staccata, finestra chiusa) readLine lancia un'eccezione o restituisce null, e in entrambi i casi il gestore viene tolto dal Set. Senza finally il server continuerebbe a scrivere a un socket morto.

Il protocollo

Una riga = un comando. Le regole le decidiamo noi

Client → serverSignificato
NICK annaMi presento (prima riga)
MSG ciao a tuttiMessaggio per tutti
QUITEsco
Server → clientSignificato
OK benvenuto annaComando accettato
ERR serve NICK nomeErrore, con il motivo
MSG anna ciaoMessaggio di anna
INFO bruno entra…Avviso del server
Un protocollo è un contratto: formato, ordine dei messaggi, risposte agli errori. Scriverlo prima del codice permette a due gruppi di fare client e server separatamente.
È lo stesso stile di IRC, SMTP, POP3, FTP e anche HTTP/1.1: comandi di testo leggibili, una riga per comando, codici o parole chiave per le risposte. Vantaggio: si prova con curl o telnet. Svantaggio: il testo è più lento da analizzare di un formato binario. Domanda: che cosa succede se un utente scrive un messaggio che contiene un a capo? Con readLine diventano due righe: il client deve impedirlo o il protocollo deve prevedere un "escape".

Al computer · 30 minuti

La chat multi-client

  1. Crea ServerChat.java e GestoreClient.java nella stessa cartella.
  2. Compila e avvia: javac *.java e poi java ServerChat
  3. Apri tre client con curl telnet://127.0.0.1:5000; nel primo scrivi NICK anna, negli altri NICK bruno e NICK carla.
  4. Da anna scrivi MSG ciao, poi chiudi la finestra di bruno senza QUIT.
  5. Collegati al server di un compagno con il suo IP.
Controllo: bruno e carla ricevono MSG anna ciao; anna no. Quando chiudi bruno, gli altri ricevono INFO bruno esce dalla chat e il server continua a funzionare.
Se il collegamento tra due PC non riesce: il firewall di Windows del PC server blocca le connessioni in ingresso (alla prima esecuzione Windows chiede se consentire Java: serve il permesso dell'amministratore). In quel caso fare le prove solo su 127.0.0.1 o usare il PC del docente come server. Errori tipici: dimenticare l'autoflush (nessuna risposta), scrivere "nick anna" in minuscolo (ERR: il protocollo distingue le maiuscole), avviare due server sulla stessa porta (BindException: Address already in use).

Mettiti alla prova

Sul server, in.readLine() restituisce null. Che cosa è successo?

  1. Il client ha chiuso la connessione
  2. Il client ha mandato una riga vuota
  3. Per 30 secondi non è arrivato nulla
  4. Il messaggio era più lungo del buffer

null significa fine del flusso: l'altro capo ha chiuso. Una riga vuota arriva come ""; il silenzio fa restare readLine bloccato (a meno di un timeout con setSoTimeout, che lancia un'eccezione).

La B è il tranello: "" e null sono diversi. Se il client si spegne di colpo (cavo staccato), il server può non accorgersene per molto tempo: niente arriva, readLine resta bloccato. Rimedi: s.setSoTimeout(ms) con un messaggio di "ping" periodico a livello di protocollo, oppure l'opzione TCP keepalive. Collegamento: è lo stesso motivo per cui WebSocket ha i frame ping e pong.

Al computer · 30 minuti

Il client Java con due thread

Un client deve fare due cose insieme: leggere la tastiera e ascoltare il server. Crea ClientChat.java:

  1. Apri new Socket(host, 5000) con i suoi stream in UTF-8.
  2. Avvia con Thread.ofVirtual().start(...) un thread che stampa ogni riga del server.
  3. Nel main leggi la tastiera e invia ogni riga; esci dopo QUIT.
  4. Prova con due ClientChat e un client curl.
Controllo: i messaggi degli altri compaiono anche mentre stai scrivendo; dopo QUIT il programma termina e gli altri vedono INFO ... esce dalla chat.
Soluzione (main): String host = args.length > 0 ? args[0] : "127.0.0.1"; try (Socket s = new Socket(host, 5000); var in = new BufferedReader(new InputStreamReader(s.getInputStream(), UTF_8)); var out = new PrintWriter(s.getOutputStream(), true, UTF_8); var tastiera = new BufferedReader(new InputStreamReader(System.in))) { Thread.ofVirtual().start(() -> { try { String r; while ((r = in.readLine()) != null) System.out.println(r); } catch (IOException e) { } }); String r; while ((r = tastiera.readLine()) != null) { out.println(r); if (r.equals("QUIT")) break; } }. Un virtual thread è "daemon": non impedisce alla JVM di chiudersi quando il main finisce. Sul terminale di Windows le lettere accentate possono apparire male: provare chcp 65001 o il terminale di IntelliJ. Estensione: il client manda da solo "NICK" con il nome passato come argomento.

Puzzle

Abbina ogni pezzo di codice al suo compito

server.accept()

new PrintWriter(os, true)
Scrive righe e le invia subito (autoflush)
readLine() == null
L'altro capo ha chiuso la connessione
ConcurrentHashMap.newKeySet()
Un Set che più thread possono modificare insieme
finally
Toglie il client dalla lista anche dopo un errore
Far spiegare a voce, per ogni coppia, che cosa succederebbe senza quel pezzo: senza autoflush il client non riceve; senza il Set concorrente si rischia ConcurrentModificationException durante l'inoltro; senza finally restano "client fantasma".

Sicurezza

Chi può leggere la nostra chat?

  • Il testo viaggia in chiaro: con Wireshark chiunque sulla stessa rete può leggerlo.
  • Rimedio di base: TLS, con SSLServerSocket e SSLSocket. Cifra il canale tra client e server.
  • Ma il server, che decifra, legge comunque tutto.

Oggi

Cifratura end-to-end

WhatsApp e Signal usano il Signal Protocol: i messaggi sono cifrati sul telefono del mittente e decifrati solo su quello del destinatario. Il server inoltra dati che non può leggere, come il nostro inoltra(), ma senza capirli.

Demo possibile (solo in laboratorio, sulla propria macchina): Wireshark con il filtro tcp.port == 5000 sull'interfaccia di loopback, poi "Segui flusso TCP": si legge tutta la conversazione. WhatsApp ha completato l'adozione della cifratura end-to-end basata sul Signal Protocol nel 2016. Collegamento con l'Unità 1 (triade CIA: riservatezza) e con crittografia simmetrica/asimmetrica. TLS in Java richiede un certificato in un keystore (keytool): esercizio possibile per i più avanzati.

Un thread per client, in grande

Con Java 21 il modello "un thread per client" torna conveniente: Thread.ofVirtual() permette a un server di tenere aperte decine di migliaia di connessioni con codice semplice e leggibile.

Discord, WhatsApp, i giochi online: tutti tengono una connessione sempre aperta verso un server, come la nostra chat. Nel browser, quella connessione si chiama WebSocket: è la prossima lezione.
Twitch documenta la sua interfaccia chat basata su IRC per i bot (molti bot di moderazione, anche basati su AI, leggono così i messaggi). Prima dei virtual thread, per migliaia di client si usavano NIO (Selector) o framework asincroni come Netty: codice più veloce ma molto più difficile da leggere. Collegamento con la lezione sul ping multiplo: i socket di java.net collaborano con i virtual thread.

Domanda classica

"Perché TCP e non UDP per una chat?" Perché serve che ogni messaggio arrivi, una volta sola e nell'ordine giusto. Per voce e video in diretta invece si preferisce UDP: un pacchetto in ritardo è inutile.

Far disegnare alla lavagna il diagramma di sequenza: anna → server "MSG ciao"; server → bruno "MSG anna ciao"; server → carla "MSG anna ciao". Aggiungere il caso di errore (comando sconosciuto → ERR solo al mittente). È un formato tipico delle prove di progetto: architettura, protocollo, scelte motivate.
